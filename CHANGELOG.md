# Changelog

All notable changes to this project are documented in this file.

## [Unreleased]

- Added a generic, nonce-correlated ownership handoff (`scripts/lib/doorbell-cutover.mjs`) between two independently-armed wake detectors, plus two concrete detectors (`scripts/lib/doorbell-cutover-detectors.mjs`) - a bounded-interval poller and an fs.watch-based watcher - and a synthetic proof harness (`scripts/doorbell-cutover-harness.mjs`) that runs an initial cutover, twenty fixed steady-state cycles, a reverse cutover, and a final reap against a scratch trigger file. A successful cutover arms the target and confirms it with a real self-test before disarming the source, tolerating a brief window where both are genuinely armed rather than risking a gap where neither is watching; a failed cutover rolls back in the opposite order. Retries are bounded by both a count and a wall-clock deadline; every wake is classified as a resumption, a dedupe within a 120 second window, a reported late duplicate outside it, or spurious. Building the two detectors surfaced and fixed two real platform behaviors: a write issued with no delay immediately after `fs.watch()` construction can miss the underlying kernel-level watch registration entirely, and a write issued essentially simultaneously with an already in-flight watch callback can be coalesced away with no separate notification of its own.
- Corrected a comment in the CI configuration that understated which checks branch protection actually requires.
- Fixed the batched process-identity read treating a single transient not-found observation as a final, confident result instead of retrying, closing an asymmetry with the single-pid read, which already retried.
- README.md now tells readers to set both Claude Code wake environment variables together: `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS` as a positive duration below the client's own MCP tool timeout, and `CLAUDE_AUTO_BACKGROUND_TASKS` enabled. This replaces guidance that split the instruction by session kind. The headline promise stays scoped to client and configuration rather than unconditional.
- Updated js-yaml to 5.2.3, typescript-eslint to 8.66.0, and the CodeQL action to 4.37.6.
- Corrected the vendored Tasks-extension schema's own description, which claimed a digest check verifies the adapter conforms to the pin. The check compares the schema file's own bytes to a recorded SHA-256 and nothing else - it never reads the adapter. A narrower version of the same overclaim in the adapter's own header, which said every result shape is checked against the schema, is also corrected: two of three result shapes are checked against the adapter's own emitted output, the third only against a hand-written literal.
- Added `config/tasks-schema-provenance.json`, binding the vendored Tasks-extension schema to the exact upstream commit and bytes it was measured against, with every deliberate divergence from that upstream source enumerated and reasoned - including several not previously written down anywhere: whole categories of upstream shapes this schema never vendors at all, a field it omits that upstream carries, several fields typed stricter than the upstream contract requires, and two fields sourced from a different spec entirely.
- Added `src/wake/resolveWakeTarget.ts`, a pure function that resolves a `WakeTarget` from the raw `_meta` object of an incoming `tools/call` request: `"resolved"` when `meta.threadId` is present and a non-empty string, `"absent"` when `meta` itself is undefined or carries no `threadId` at all, `"malformed"` (with a reason naming what was actually found) when `threadId` is present but is null, a number, an object, an array, or an empty string. `threadId` is treated as a thread-identity signal by this codebase's own design; the function makes no claim about which real client populates it or how. Any handler-visible metadata object lacking `threadId` resolves to the `"absent"` case rather than an error - a fact about this resolver, not a claim about any particular client's shape. Never validates `threadId`'s shape beyond "present and a non-empty string" and never falls back to anything else (an env var, a config guess, a correlation heuristic) when a target cannot be extracted - a caller holding anything other than `"resolved"` has definitively not been given a target. `scripts/check-module-boundaries.mjs`'s `FROZEN_MODULES` now also admits this file.
- Added the transport-layer wake: a mechanism distinct from the MCP notifications sent down an open connection, for eventually resuming an idle agent session on the host machine. `src/server.ts` resolves each `run` call's `WakeTarget` from that request's own `ctx.mcpReq._meta` and passes it to `src/tasksAdapter.ts`, which subscribes a dedicated, independent listener to the job's terminal transition - registered regardless of whether the calling connection negotiated the Tasks-extension capability, since the mechanism never sends an MCP notification down that connection and the underlying job exists either way. The listener unsubscribes itself the instant it fires, so it never outlives the job's own terminal transition. It calls the transport selector only when an internal server-process environment variable is set to the exact string `"1"` (never something an MCP client can set over the wire) and the request's own metadata resolved a target; a malformed target is logged and never acted on, and the call itself is fire-and-forget, never affecting the `tools/call` response it rides alongside. The variable is unset by default, so the mechanism ships inert - the subscription and its listener lifecycle are real, but no transport call happens unless that variable is explicitly set. `src/wake/resolveWakeTarget.ts` is a third admitted public door into `src/wake/` (module-boundary and wake-transport-boundary guards updated to match) since `server.ts` now calls it directly.
- Fixed a real race in `kill_confirmed`'s own write path: `setKillConfirmation` carried a guard that silently discarded a real, external confirmation whenever the eager reap at process exit resolved before the record's own terminal-state transition - Node's `exit` event can fire before either stream's `end` event, so this raced routinely, and once the write was lost, the reap-once tracking had already consumed its one attempt, leaving `kill_confirmed` stuck at `undefined` permanently rather than merely late. The field's own contract never depended on the record's state in the first place - `confirmed` reflects the caller's own knowledge at the moment of the call, whether that is a genuine external check or, for a job that never spawned, a vacuous truth by construction - so the guard was only gating on whether this store's own bookkeeping had caught up, never protecting against a false confirmation; removing it closes the race outright, since no call site can now record a false positive for a group that is genuinely still alive. As defense in depth for the same class of guard elsewhere, the three call sites that gate the reap-attempt flag on the confirmed outcome now gate on the outcome AND the write having actually landed. Those two conditions serve two different purposes: the outcome half is what already lets an unconfirmed, still-live job be retried on a later call; the write-landed half is stale-bookkeeping cleanup for the narrower case where the record itself vanishes out from under a confirmed write (the only production path today is a lazy TTL purge racing an in-flight reap) - `markReapAttempted` has no existence check of its own, so without this half it would still add a reap-attempted entry for a job id `get` can no longer find. A job that never spawned - an invalid cwd, unresolvable executable, or policy denial (settled synchronously as part of the job's own creation), or a genuine async spawn failure past those checks (settled as part of its terminal transition) - now settles `kill_confirmed` to `true` rather than leaving it unset forever, since its process group trivially holds zero members.
- Fixed two further never-spawned paths that omitted the same `kill_confirmed` settling call: a job cancelled while still waiting in the concurrency queue, and a job still queued when the server shuts down. Both settle straight to `killed` without ever spawning a process group, matching every other never-spawned case, but a status-only client polling either kind of cancelled job previously saw `kill_confirmed` simply absent instead of `true`. Regression coverage for the queue-cancellation path now asserts the public projection through real `kill()` and `status()` handler calls, plus a `list()` call checked against its own five-field summary - `list()` was never meant to carry `kill_confirmed` for any job, so that call only confirms the job left the queue, not the field's value. The shutdown-drain path is asserted through a direct `status()` handler call taken after the client transport has already closed, since there is no `kill()`, no `list()`, and no post-shutdown RPC to call there.
- Fixed a real, measured test race in `test/tasks.test.ts`'s run-only-mint-rule test: a naturally-exited job's `state` could read as terminal before its `counts.stdout_lines` had actually caught up, because the test polled only until `state` turned terminal and asserted line counts as if that same poll had covered them too - observed on CI as a job that had already written one byte still reading a `stdout_lines` count of 0. Added a poll that waits for a job's `counts` to hold steady across several consecutive reads before treating them as final (sound because the underlying counters only ever increase), applied it and the existing `kill_confirmed` poll wherever that test reads either field, and found the identical `kill_confirmed` exposure in `test/run.test.ts`'s own direct-handler tests, which spawn through the same code path. Every genuinely safe read is left alone with an inline note explaining why. No production behavior changed - the materialization these tests exercise is correct as built; these were gaps in how the results were read.
- The README now states, per connection era, which Tasks-extension methods currently dispatch. On a legacy (pre-2026-07-28) connection, `tasks/get`, `tasks/update`, and `tasks/cancel` all reach their handlers. On a 2026-07-28-revision connection, only `tasks/update` currently dispatches - the revision's method registry has no entry yet for `tasks/get` or `tasks/cancel`, so a request naming either returns `-32601 Method not found` regardless of capability. The seven tools (`run`, `status`, `output`, `tail`, `kill`, `list`, `follow`) and the poll floor they sit on are unaffected either way; so is the Tasks-capable output/status notification path.
- The README's description of the Tasks-capable terminal status notification now states, in terms, where the mechanism falls short of the released spec. The notification's payload matches the legacy `tasks/get` projection field for field. But on a 2026-07-28 connection, `tasks/get` itself currently returns `-32601 Method not found`, so there is no live method there for the notification to be compared against. And this server sends the notification unconditionally to the Tasks-capable connection that minted that task - not broadcast to other connections - rather than following the released subscription protocol's task-id opt-in and per-client acknowledged subset.
- Added `follow`, a 7th tool: a bounded wait on a job's next event, returning as soon as new output arrives on the selected stream(s), the job reaches a terminal state, or an explicit `timeout_ms` elapses (defaulting to 45000ms, clamped to a 3600000ms/one-hour ceiling), whichever happens first - a timeout is a normal, non-error result, never a hang, and `status`/`output`/`tail` remain the way to check a job regardless of whether `follow` is ever called. Output arrival means a newly materialized line on the selected stream; a buffered fragment without a terminator does not wake the call on its own, but becomes a partial event when the selected stream finalizes; terminal state can still settle the call. Subscribes to `jobStore`'s own `onOutputArrival`/`onJobTerminal` seams synchronously, before ever checking whether either condition is already true, so nothing can arrive in the gap between "read current state" and "start listening": no other callback can run between those two synchronous steps on a single-threaded event loop, even though the steps themselves still take real time to execute. `stream` scopes the underlying subscription itself, not just the response, so an arrival on an unselected stream never ends the call early. Cancelling the underlying MCP call - closing the connection, or a client sending the standard cancellation notification - now tears down its subscriptions and pending timer immediately rather than leaving them to run to their own natural bound. The server also caps how many `follow` calls may be outstanding at once, across every connection it serves, at 128; a call made once that cap is reached is rejected outright with a tool error, never queued or coalesced with an existing wait on the same job - the cap is enforced process-wide rather than per connection, disclosed as such, since this server tracks no per-connection identity today.
- Fixed a real, reachable gap in `follow`'s cancellation handling: the installed SDK's own `notifications/cancelled` dispatch treats a request id of `0` or `""` (empty string) as absent (its guard is a plain truthiness check, and both are falsy in JavaScript), even though JSON-RPC 2.0 allows either as a legal request id with no reservation on them - so a client whose `tools/call` happened to carry one of those two ids could never have that call's cancellation reach `follow` through the SDK's own path, no matter how correctly the server forwarded its signal, and the call's output/terminal subscriptions and admission-budget slot stayed held until the underlying job reached a terminal state, the call's own timeout elapsed, or the connection closed. Reproduced directly against the installed SDK's own source, and pinned down with a raw-wire test that sends a real `notifications/cancelled` naming `requestId: 0` and, separately, `requestId: ""` over an actual transport, paired with an identical nonzero-id case as a control. Fixed with a second, independent observer chained onto the same wire traffic the SDK's own dispatch already reads, checking a cancellation's `requestId` by type rather than by truthiness, so a falsy id's cancellation is now caught regardless of what the SDK's own guard does with it; every other request id keeps behaving exactly as before, since the two signals are combined with `AbortSignal.any`.
- Fixed a second, narrower gap in the same mechanism: the installed SDK defers actually invoking this server's `tools/call` handler to a microtask, after already registering its own internal cancellation state synchronously, while the new independent observer above runs synchronously on message receipt - so a client sending its `tools/call` request and that same request's `notifications/cancelled` back to back, with no yield between the two sends, could have the cancellation fully processed and discarded before this server's own tracking for that request even existed, letting the call subscribe and hold an admission-budget slot with nothing left to ever cancel it. Reproduced with a raw-wire test that sends both messages with no `await` between them, for both `0` and `""`, and confirmed the call's listeners and admission slot never settle. Fixed by having the observer record an early cancellation it cannot yet apply, consumed the instant the handler registers its own tracking - closing the race regardless of which side happens to run first, bounded by a fixed cap against a client naming request ids that never arrive at all.

- Added `src/wake/appServerTransport.ts`, a concrete `WakeTransport` that wakes an idle Codex thread by spawning the `codex app-server` subcommand and driving its newline-delimited JSON-RPC protocol over that subprocess's own stdio (one JSON object per line, no `Content-Length` framing - confirmed by spawning a real, stock `codex app-server`, CLI 0.147.0, and reading its raw stdout bytes). Sending `thread/goal/set` with `status: "active"` for an idle thread starts a model turn there, with the caller's objective text reaching the model verbatim; `probe()` verifies at runtime, on every call, that the running app-server's `experimentalFeature/list` actually reports the `"goals"` feature enabled, never assuming it stays true across a restart of the process it probes. Everything this transport touches is a closed, undocumented internal of the app's own bundled code rather than a published API, and it is fenced accordingly: `probe()` checks, in order, that the socket path exists, is actually a socket, is owned by this process's own uid, and genuinely answers a real `initialize` call, failing soft with a specific diagnostic on any deviation rather than crashing or guessing; the socket path itself already relocated once, inside a single app update earlier today, from an older per-uid temp path, and that same update silently dropped an unrelated local feature entirely, both disclosed directly in this file's own header. The owner gate `thread-owner-discovery` enforces - only a client with the conversation genuinely open in a live window may start a turn on it - is honored rather than routed around: a missing owner (measured today as a `no-client-found` result for every thread not currently open in a window) reports `refused`, never forged or retried into looking like a hang, and `thread-follower-start-turn` is never attempted without a real owner id the discovery call itself returned. This transport reads no credential, makes no network call, and requires no pairing; its whole authorization model is being the same OS user as the socket's owner. It implements no preference ordering against the separate, durable `codex app-server`-based transport a sibling story is building - that selection logic remains out of scope for both. Tested against a fake local Unix domain socket server built independently of this transport's own framing code, covering the wire round-trip (chunked/multi-frame/partial delivery, an oversized declared length, malformed JSON), the owner-gate and its race with a closing window, and every fencing branch `probe()` checks.
- Added `src/wake/wakeTransport.ts`, the single `WakeTransport` contract every future wake mechanism will implement (`probe(): Promise<Capability>`, `wake(target, payload): Promise<WakeResult>`), plus a boundary guard (`scripts/check-wake-transport-boundaries.mjs`) that keeps every transport-specific symbol confined to its own file and its own tests, enforced in CI alongside the five existing source guards. `probe()` must report a real, freshly-observed result (never a platform guess) with a stated reason on failure, and is never cached by the interface itself - the caller states and justifies its own cache lifetime, if any. A wake result distinguishes delivered, refused, and unavailable as three separate outcomes rather than collapsing to a boolean, since "this will never work here" and "this failed just now" call for opposite remedies. This module is purely type-level - it compiles to an empty runtime file - so it adds zero transports and zero runtime cost on its own; ghantika continues to start and serve its existing tools exactly as before with none registered, which is the supported baseline this and every future transport are built against. This is not `src/tasksAdapter.ts`'s own output-driven wake-on-output mechanism (`notifications/ghantika/outputWake`) or the released Tasks extension's own `notifications/tasks` status notification, both unrelated pre-existing features that happen to share the same English word.
- `kill_confirmed` is written by an async confirmation callback whose gap versus the calling response is real event-loop scheduling latency with no stated upper bound, documented as such in `src/tools/kill.ts` - so a fixed wall-clock deadline on that field settling is a bound on a quantity the contract says has none, and one lost on a loaded CI runner. Nine call sites across `test/tasks.test.ts`, `test/kill.test.ts`, and `test/run.test.ts` now poll `kill_confirmed` without a time limit instead, all removing a `Date.now()`-based deadline that previously threw once exceeded: `test/tasks.test.ts`'s shared `pollUntilKillConfirmed` helper, used at 2 call sites; 4 further sites in `test/kill.test.ts` with the identical inline shape; and `test/run.test.ts`'s own shared `pollUntilKillConfirmed` helper, used at 3 call sites, carrying the identical deadline-plus-throw shape as the other two files' sites. Every site relies on the surrounding test's own runner timeout as the backstop for a genuine hang, and logs a one-line breadcrumb to stderr on a fixed cadence while still waiting, carrying the same job snapshot the old failure message did. A new check, `scripts/check-no-bounded-kill-confirmed-wait.mjs`, detects the specific pattern that caused this: a loop referencing `kill_confirmed` that also contains an `if (Date.now() > ...)` guard followed by a `throw`. It does not detect an equivalent deadline built from a different clock source (an aliased or global `Date.now`, `performance.now()`) or a control-flow shape other than `if`-plus-`throw`.

### Added

- **`follow`, a seventh tool for a bounded wait on a job's next event**: new output on a chosen stream, the job reaching a terminal state, or an explicit `timeout_ms` (default 45000ms, capped at one hour), whichever comes first. A timeout is a normal, non-error result; `status`, `output`, and `tail` remain the way to check a job regardless of whether `follow` is ever called. The server caps outstanding `follow` calls at 128 across every connection it serves; a call made once that cap is reached is rejected immediately rather than queued. Cancelling the underlying MCP call tears down its subscription and any held slot right away, including for a client whose `tools/call` request carries an id of `0` or an empty string, a case the installed SDK's own cancellation dispatch otherwise misses.
- **A wake transport layer for resuming an idle agent session**, distinct from the plain poll surface: a `WakeTransport` contract (`probe()`/`wake()`, with delivered, refused, and unavailable as three separate outcomes) backs two concrete transports, tried in order with a refused, unavailable, or thrown attempt on one falling through to the next rather than stopping there, and stopping only at the first delivery. One wakes an idle Codex thread by spawning `codex app-server` and driving its documented JSON-RPC protocol; the other wakes a Codex conversation open in the ChatGPT desktop app over that app's own local IPC socket. `docs/wake-support-matrix.md` documents what has actually been observed for each route, including Claude Code's own client-side auto-background of a held `follow` call: the setup each needs, the real limits of each, how to reproduce the result, and that a first `follow` call in a brand-new session may not background. The poll floor (`status`, `output`, and `tail` answering any initialized client, no wake-specific setup required) is unaffected either way, and is stated up front so nothing in the matrix reads as a requirement for correctness. The mechanism ships inert by default, gated behind `GHANTIKA_WAKE_TRANSPORT_ENABLED`, a server-side environment variable no client can set over the wire.
- **Tasks extension support (`io.modelcontextprotocol/tasks`)**. The server advertises the capability, and `run()` returns a task handle instead of the plain `{job_id}` reply whenever a Tasks-capable call actually creates a job; a call the concurrency cap rejects creates no job and returns its ordinary rejection unchanged, regardless of capability. For a legacy connection, capability is a one-time declaration at `initialize` covering every call for that connection's life; for a connection served under the MCP 2026-07-28 revision, which has no `initialize` exchange to declare anything in, capability is read from each individual `tools/call` request's own metadata instead, so only that one call is governed by it. Every other tool, and the plain poll surface, stay byte-identical on every connection regardless of capability. `tasks/get`, `tasks/update`, and `tasks/cancel` are implemented against the extension's released 2026-07-28 contract; only the `extensions` bag that contract specifies is honored, not the SDK's own deprecated pre-2026-07-28 declaration. A capable client also receives a notification on a task's terminal transition and a coalesced wake on new output, both strictly additive to the existing poll surface. The extension's result schema is vendored in-repo with a recorded upstream commit and digest, and every deliberate divergence from that upstream source is enumerated and reasoned in `config/tasks-schema-provenance.json`.
- **A concurrency cap and bounded admission queue in front of `run()`'s spawn.** A job arriving while the cap is full and the queue has room reports `starting` with a new `queue_position` field; one arriving once both are full is rejected immediately, with no job ever created. `run()` never waits for admission, spawn completion, or command execution before returning. A queued job's position is visible through `status` and `list`; `list` also reports the current cap.
- **Retention for a finished job's buffered output.** It becomes eligible for reclamation once `GHANTIKA_JOB_RETENTION_MS` milliseconds have elapsed since the job ended (default one hour) or the number of eligible finished jobs exceeds `GHANTIKA_MAX_RETAINED_JOBS` (default 200), whichever comes first. A still-running job's output, and a job's own record (`status`/`list`), are never touched by this. `output`/`tail` disclose reclaimed content the same honest way they already disclose an ordinary byte or line-cap eviction, never a bare not-found that would read identically to a job id that never existed.
- **A command allowlist policy.** For an argv-array job, `run` checks the command's fully resolved executable path (PATH lookup, symlinks followed) against an operator-configured allowlist, loaded from a JSON file named by the `GHANTIKA_POLICY_FILE` environment variable, before it ever spawns anything. For a shell-string job, that same allowlist instead gates the fixed, resolved platform shell binary (`/bin/sh` on POSIX, the resolved `ComSpec` on Windows) that will run the string; the string's own contents play no part in the decision. The default with nothing configured is to deny every command. A denied command settles as a failed job immediately, with a diagnostic naming the denial, and never reaches the real process spawn.
- **`GHANTIKA_CWD_ROOTS`**, scoping `run` to an operator-configured set of allowed working directories. A candidate `cwd` is compared against each configured root by its real, symlink-resolved target, never a literal string prefix, so a directory reachable only through a symlink is judged by where it actually points.
- **An optional `deadline_ms` on `run`.** A job still running once that many milliseconds have elapsed is terminated and settles `failed` with the same closed diagnostic-reason shape every other failed job carries. On POSIX this termination is, in the ordinary case, gated on the same pre-signal identity check `kill()` itself applies: when the check cannot safely proceed (the process is already gone, or a genuine identity mismatch), the deadline refuses to signal rather than terminate an unrelated process, and the job's real outcome is recorded by whatever already-in-flight event explains it. On Windows there is no equivalent identity check on this path; the deadline terminates the process tree directly. Omitting the field leaves a job's behavior completely unchanged.
- **Public CI on GitHub-hosted runners**: build, typecheck, lint, and an operating-system by Node-version test matrix, plus CodeQL, semgrep, zizmor, and actionlint, all aggregated behind one required `gate` check, alongside a blocking Prettier format check and a coverage job with an absolute per-metric floor. A separate `Main Verify` workflow runs the same matrix on every push to `main`, so a defect that lands there is caught even between pull requests.
- **Process identity reporting on `status`.** A `pid` field reports the OS process a job was tracked against, once it ever had one, always alongside a `birth_identity` state (`pending`, `captured`, or `unavailable`), so a stale-looking pid can be verified against a real captured identity rather than trusted on its own.

### Changed

- **`kill()` signals a job's whole process group**, not only the tracked leader: SIGTERM, a bounded grace period, then SIGKILL if anything in the group is still alive. Before escalating a `kill()`'s grace-period SIGTERM to SIGKILL, ghantika checks whether the process group is still the one it spawned: a leader-plus-descendant identity snapshot taken right before the SIGTERM is compared, via one batched read, against a fresh read once the grace period ends; if none of the recorded members still shows a matching start time, escalation is refused and no SIGKILL is sent, disclosed via a new `escalation_refused_reason` field. This is a bounded, conservative check rather than a guarantee: a failed or degraded observation always refuses escalation instead of defaulting to it, and an unresponsive `ps`/`pgrep` is force-reaped rather than left running.
- **Birth-identity comparison is platform-specific.** On Linux, the tracked job leader's own birth identity is confirmed against `/proc/<pid>/stat`'s own raw kernel start-time counter, compared for exact equality with no unit conversion, closing a class of bug where a virtualized guest's clock sources could disagree under the elapsed-time computation `ps -o etime=` performs internally. On POSIX, a process group's other members are instead revalidated through one batched `ps` read of their own start times. macOS continues to compare the leader's own real, `ps`-observed elapsed-age reading within a tolerance window, since macOS has no equivalent `/proc` filesystem.
- **`kill_confirmed` and `identity_confirmed` report exactly what a real, external check observed.** Each is a different kind of check (a `pgrep`-based process-group read for `kill_confirmed`, a birth-identity read of the tracked leader for `identity_confirmed`), and neither is a whole-tree guarantee: a descendant that escaped the process group is invisible to either. A job that never spawned a process group at all, including one cancelled while still queued or still queued at server shutdown, settles `kill_confirmed` to `true` vacuously, since its group trivially holds zero members. Neither field is ever `false` while a real answer is still pending; a caller sees it simply absent until it settles.
- **`output` and `tail` disclose loss and truncation more precisely.** `dropped` counts every discrete loss event a stream has suffered, an evicted line, a discarded pending fragment, or a chunk that arrives after a job's output was already reclaimed, rather than only a materialized-line count, so sub-line loss is never silently invisible. `truncated: true` also fires when a call's own `limit` or `lines` argument left more already-available events undisclosed, distinct from genuinely losing history. The combined stdout-and-stderr view numbers events from one real, stable sequence counter shared per job, so a cursor from one call keeps matching the same lines on a later call that reuses the same stream selection, even after older lines have been evicted; switching stream selection can skip an already-retained event on the other stream, so a caller changing selection should restart from a fresh cursor rather than reuse one from a different selection.
- **A job's client-visible terminal state is ordered after its own last output event for `exited` from a normal exit, or `killed` from a signal the job received from outside this server**, whenever the reap that observed its process group empty is confirmed and no descendant has left the group: already-buffered output has fully drained, and any backgrounded grandchild inheriting the job's stdio has already closed it, by the time the terminal state becomes visible to a caller. A `kill()` this server itself performs is different by design: it claims the terminal state synchronously the instant the signal is sent, so a job it killed is never misreported as merely exited, and output the process writes while handling that signal can arrive after the terminal state is already visible.
- **The server serves the MCP 2026-07-28 revision's `server/discover` opening exchange alongside the existing legacy `initialize` handshake.** Which era a connection uses is decided once, at that connection's own opening exchange, and pins the rest of that connection's behavior for its lifetime; a client that falls back from an optimistic `server/discover` probe to `initialize` gets a fresh instance built the same way. The `-32700`/`-32600` error replies (unparseable JSON, or JSON that parses but fails the base JSON-RPC envelope) are produced ahead of the real transport, on a single raw-stdin classification shared by both eras rather than two separate mechanisms.
- **Tasks capability negotiation is era-specific.** A legacy, pre-2026-07-28 connection declares Tasks support once, at `initialize` time, for its whole lifetime. A connection served under the MCP 2026-07-28 revision has no `initialize` exchange to declare anything in; capability is read from each individual `tools/call` request's own metadata instead, so only that one call is governed by it, never the connection as a whole. On both eras, a client declaring Tasks support only through the SDK's deprecated `capabilities.tasks` field, the obsolete 2025-11-25 wire vocabulary, never has a task minted from that declaration.
- **The Tasks-extension notification layer uses the released contract's own wire vocabulary**, kept separate from ghantika's own output-delta wake. The output-delta wake, the coalesced per-batch stdout/stderr accelerator (firing on stderr output the same way it already does on stdout, so a command that reports progress only on stderr does not leave a capable client waiting silently), is sent under its own explicit, non-spec method name, `notifications/ghantika/outputWake`, so it cannot be mistaken for extension traffic. A spec-conformant `notifications/tasks` notification fires on every task's terminal transition, carrying the same complete task snapshot `tasks/get` would return at that instant, delivered to every Tasks-capable connection for a task it minted, since the installed SDK's own `subscriptions/listen` routing has no support for the extension's per-task-id filter.
- **Moved typechecking and building onto TypeScript 7** through a side-by-side compatibility layer: `typescript` resolves to a thin TypeScript 6 compatibility package (`npm:@typescript/typescript6@6.0.2`), while a separate `@typescript/native` entry carries the real 7.x compiler that `tsc`, `npm run build`, and `npm run typecheck` actually run against, the layout TypeScript's own 7.0 release describes for this situation. An editor's language service reads the `typescript` package, so it runs on 6.x even though the command line compiles with 7; `typescript-eslint`'s declared peer range still excludes TypeScript past 6.1, and this layout routes around that constraint rather than lifting it. The compatibility package resolves to 6.0.2, the highest version it publishes; it in turn pulls in real TypeScript 6.0.3, the newest release every one of `typescript-eslint`'s peer-declaring packages admits under their declared range.
- `npm test` and `npm run coverage` now run through `scripts/run-tests.mjs`, a custom test-file discovery and execution wrapper, in place of a shell glob.
- **CI's test matrix runs `ubuntu-latest` and `macos-latest`, each against Node 22 and 24.** There is no Windows CI signal right now, no hosted leg, no VM, no nightly substitute. The Windows-specific code paths (process-tree kill, executable-extension resolution) remain live production code with no CI coverage on that platform.
- **The module-loader guard matches a forbidden primitive at its acquisition site by real, resolved symbol identity rather than by invocation shape.** Every route to a small set of forbidden JavaScript primitives is flagged at its acquisition site, including three routes a specifier-string match cannot see: `createRequire` acquired via `process.getBuiltinModule`, the `Function` constructor reached via an ordinary function's own `.constructor`, and the global `eval` reached via `Reflect.get(globalThis, "eval")`. It is disclosed as a hop-bounded hygiene check rather than a security boundary: a second hop of alias or computed-member acquisition is an intentionally open, tracked route this guard does not chase, and the `node:module` import routes to `createRequire` still match by literal specifier text rather than resolved identity.
- `npm run lint` now targets this project's own source directories (`src`, `scripts`, `test`, `eslint.config.js`) instead of the whole working tree.
- **Dependency and security updates**: `js-yaml` (fixing GHSA-pm4m-ph32-ghv5, an exponential-time parse on crafted input; a devDependency-only exposure, since the shipped package has no runtime dependency on `js-yaml`), `typescript-eslint`, the CodeQL action, `eslint`, `globals`, `@types/node`, `actions/checkout`, `actions/setup-python`, and Prettier all carried forward to current releases, and the `@modelcontextprotocol` SDK bumped to its released 2.0.0 GA version. CI's pinned `semgrep` version is kept current the same way; `zizmor` is bumped because its prior pinned release was withdrawn by its own publisher.

### Fixed

- **A real race in `kill_confirmed`'s write path**: an external confirmation could be silently discarded when an eager reap at process exit resolved before the record's own terminal-state transition landed, permanently stranding the field rather than merely settling it late. The guard causing this is removed outright, since the field's own contract never depended on the record's state in the first place.
- **A false process-group kill error on macOS**: a job's process group can exit in the narrow window between the shutdown handler's own liveness check and the signal send; the signal call then reports `EPERM` rather than the already-handled `ESRCH` for this exact case, and it is now recognized rather than misreported as an unexpected error.
- **A transient birth-identity capture miss on a contended host**: a freshly-forked child is not always yet visible to the very first `ps` observation, and that single miss could permanently settle a job's identity as unavailable. The capture now retries a "not found" observation for up to 1000ms, bounded so a retry can never itself run past the total-settlement guarantee `kill()` and the shutdown reaper both depend on.
- **`README.md` states, in terms, where the Tasks-extension notification mechanism falls short of the released spec.** On a 2026-07-28-revision connection, only `tasks/update` currently dispatches; the revision's method registry has no entry yet for `tasks/get` or `tasks/cancel`, so a request naming either returns `-32601 Method not found` regardless of capability. The terminal-transition notification is sent unconditionally to the connection that minted a task, rather than following the released subscription protocol's per-client, task-id opt-in, since the installed SDK's own routing has no support for that filter.

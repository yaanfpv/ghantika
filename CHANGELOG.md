# Changelog

All notable changes to this project are documented in this file.

## [Unreleased]

- Bounded the nested `node --test` run inside `test/loader-escape-matrix.test.ts`'s permanent-guard check with a 45-second timeout (a healthy run measured in the single-digit seconds on this machine across repeated runs, varying with host load - comfortable headroom under typical conditions, staying well inside this repo's existing 120-second per-test/15-minute per-job CI ceilings even at the slower end observed), classified via the specific `ETIMEDOUT` error code rather than a bare signal check so a `maxBuffer` overflow or an ordinary external signal is never misreported as this call's own timeout, and named the nested run itself in the resulting diagnostic. `ETIMEDOUT` proves only that the run did not finish inside its configured duration, not that it was genuinely stuck rather than legitimately slow, so both the thrown message and this description describe the observed timeout rather than asserting a hang. This bound trades in the other direction too: a legitimately slow-but-not-hung run under host contention, which the previous, more generous outer ceilings would have let finish, can now be killed and reported the same way. The four new tests driving this classification are fixture-driven - they prove the helper's own classification logic and messages given a real child-process result, but do not observe the production call's own configured timeout value or its own call to the classifier, so deleting either from that call site would not be caught by this suite; covering that call path is tracked as separate follow-up work. Also corrects this guard's own comment, which previously described the nested files as running in worker threads (each runs as its own child process under the supervisor, Node's default process-isolation mode, confirmed directly) and scopes its SIGTERM-reaping observation honestly as one manual, single-host reproduction rather than a tracked, cross-platform proof.
- Added a concurrency cap and a bounded FIFO queue in front of `run()`'s spawn, so a burst of jobs runs under an honest, configurable bound instead of exhausting the host. A job arriving while the cap is full and the queue has room reports the existing `starting` state with a new `queue_position` field rather than a sixth job state; one arriving once both are full is rejected immediately, with a typed diagnostic and no job ever created - `run()` returns instantly in every case, never blocking on a slot. A concurrency slot is held for as long as a job is running or still being cleaned up after exit, released only once its process-group reap has actually confirmed the group empty. A reap that runs but cannot confirm leaves the slot held, tracked as stranded and retried automatically a bounded number of times, or separately recoverable by a manual `kill()` call against the same job. Neither retry path ever sends the group a further signal, though: by the time a retry runs, this server can no longer confirm the tracked process-group id still names the group it originally spawned rather than an unrelated one that has since reused it, so a retry only ever re-checks existence. A group still genuinely alive at that point stays a disclosed, unconfirmed residual instead of receiving a second signal; one that has since genuinely emptied is correctly recognized and recovered, still without ever being signaled again. The task-record TTL purge never reclaims a job while its slot is still stranded, so the only durable trace of a held slot is never silently erased before it can be recovered - a job becomes purgeable again the moment its slot is actually confirmed. A job that fails to spawn once it reaches the front of the queue settles to `failed` and its slot is freed rather than left stuck. On shutdown, any jobs still waiting in the queue are killed and the queue is drained rather than left in limbo. Each queued job's position is now visible through `status` and `list`; the current cap through `list`. Admission is checked only after `run()`'s existing cwd/executable/policy validation has already passed, so a denied or otherwise-rejected command never occupies a concurrency slot or a queue position. A signal-capable process-group reap that throws before recording its outcome is now still treated as an entered attempt, so a later retry against that same job is never routed back through a signal-capable reaper a second time. A job that never reserved a slot at all - one whose invalid cwd, missing executable, or policy denial settled it to `failed` before admission control ever ran - could still have its terminal `kill()` call decrement the shared active-slot counter, silently freeing a different, genuinely-running job's reservation and letting real concurrency exceed the configured cap; a slot is now released only for a job id this store itself recorded as having actually reserved one.
- Carried four pinned GitHub Actions and Prettier forward to their current releases: `actions/checkout` v7.0.0 to v7.0.1 (fourteen sites in `ci.yml`, one in `main-verify.yml`), `actions/setup-python` v6.3.0 to v7.0.0 (two sites), `github/codeql-action`'s `init` and `analyze` v4.37.0 to v4.37.4 together (the pair pins to the same commit), and Prettier 3.9.5 to 3.9.6 in both `package.json` and the lockfile. The setup-python major bump migrates the action itself to ES modules and drops its unused `pip-install` input; neither of our two call sites uses that input, so the migration needs no change on our side - the existing v6.3.0 pin already required the Node 24 action runtime GitHub-hosted runners provide, and v7 adds no new runner floor. Whether the two affected jobs pass under v7 is confirmed by CI once this lands, not by anything run locally. The Prettier bump reformatted nothing - every tracked file it checked came back unchanged.
- Named which of 15 distinct diagnostic labels, across the three process-observer functions that could each previously fail silently, actually produced a given occurrence: `captureBirthIdentityPosixAsync` (6 labels - the one feeding `kill()`'s pre-signal `identity_confirmed` guarantee), `readPidStartTimesBatchPosix` (2), and `captureEscalationIdentitySnapshot` (7, covering its three capture steps and whether each ran out of budget before starting or failed once running). Every label distinguishes a genuine observer failure from that observer's own timeout mechanism firing, and each log is diagnostic-only (`console.error` to stderr, never `console.log`, since stdout carries this server's MCP protocol) - no return value or control flow changes on any of the three functions. Which label actually fires on a real, intermittent CI occurrence is still unestablished; this instruments attribution, it does not itself resolve the underlying defect.
- Fixed a real Linux-only misclassification the diagnostics above surfaced: `captureBirthIdentityPosixAsync`'s retry-loop classifier decided between `aggregate-exhausted-mid-observation` and `observer-genuine-failure` by checking whether an observer's own reason string started with a fixed POSIX-`ps` prefix (`"ps did not settle within"`). On POSIX that prefix is genuinely present on every timeout path by construction, so the check worked there - but Linux's own `/proc/<pid>/stat` reader times out with a different reason (`"/proc/<pid>/stat did not settle within ..."`), which never matched, so every Linux observation cut short by the aggregate budget was silently reported as a genuine observer failure instead. Fixed by adding a structural `timedOut: boolean` field to the observer-failure variant of the three affected result types, set explicitly by each platform-specific observer at its own construction site rather than inferred from wording, and switching the classifier to read that field. The old string constant stays, now purely descriptive text inside the reason string itself, with no role in classification - a future platform's observer cannot reintroduce this class of bug by choosing different wording, since the type requires `timedOut` regardless of what the reason says.
- The nine tests covering this classification previously simulated the failure on Linux by shadowing `ps` on `PATH`, a technique that cannot reach Linux's capture path at all (it goes through `/proc`, never `ps`), so they skipped there instead of asserting anything. Converted to genuine Linux-native assertions using the existing `GHANTIKA_TEST_DEGRADE_PROC_READ` test-only failure-injection hatch, each matched to its original non-Linux test's exact failure semantics (not-found, observer-failure, or a not-found-then-hang shape for the mutation-strong regression proof of the fix above). `test/skip-baseline.json` no longer lists any of the nine under `linux`, since they now genuinely execute and pass there.
- The new diagnostic also accepts an optional hook reporting how much other spawned-process load this process was carrying when a failure happened. `run()`'s handler supplies one backed by a count of other jobs with a real, currently-tracked spawned child - excluding both the job under test itself and any job already in a terminal state, since `markExited` never removes a job's entry from the tracked-children map.
- Bumped the pinned semgrep version used by CI from 1.171.0 to 1.172.0. Running 1.172.0 directly against this repo found the same 0 findings across the same 248 rules and 48 tracked files that the previous pin found, so this catches the pin up to an already-verified-equivalent version rather than taking an unverified jump.
- `run` now checks every command against an operator-configured allowlist before it ever spawns anything, on both platforms this project supports argv-array and shell-string invocation on. The allowlist is loaded from a JSON file named by the `GHANTIKA_POLICY_FILE` environment variable - never from anything in the tool call's own arguments - and the default with nothing configured is to deny every command, not to allow one. A command is judged by its fully resolved, real executable path (PATH lookup, symlinks followed, case- and separator-normalized), so no amount of respelling a denied binary's name changes the outcome, and `shell: true` is judged on the actual platform shell it invokes rather than treated as a separate, weaker path - and that exact resolved path, not a re-derived one, is what the real spawn is told to launch, so a job's own environment can never point the launch at a different executable than the one this check approved. A denied command settles as a failed job immediately, with a diagnostic naming the denial, and never reaches the real process spawn. A missing or broken policy file also denies everything rather than falling open. Disclosed limitation: this check runs against the executable's resolved path moments before the real spawn, which still re-opens that same literal path itself (or, for an ordinary argv command, still re-resolves a bare name against it); a filesystem change landing in that narrow window is not something this closes. Also disclosed: this codebase ships no default allowlist at all, so nothing here inspects what an operator-allowlisted interpreter (a shell, `env`, and the like) is subsequently asked to run - allowlisting one of those is a deliberate choice an operator makes for their own deployment, the same trust they'd be extending by running it directly. Also disclosed: the Windows `shell: true` path (resolving the platform shell from this server's own trusted `ComSpec`/`PATH`, never a job's own environment) is verified by reading and by a platform-mocked unit test, not by real execution - CI carries no Windows leg right now (see below).
- Added a `Main Verify` workflow (`.github/workflows/main-verify.yml`) that runs the same OS x Node test matrix `ci.yml` runs on every pull request, on every push to `main` as well. `ci.yml` only ever triggers on `pull_request`, so previously a defect that landed on `main` stayed invisible until some later, unrelated PR happened to trip over it - and it would surface there looking like a defect in whatever landed most recently, not in whatever actually introduced it. This is detection, not prevention: a red run here means a defect already landed and was invisible until this ran, not that anything was stopped from merging, and it will not catch an intermittent that happens to pass its own run too. On a genuine failure it opens or updates a single tracking issue naming the exact merge commit and linking to the run, rather than leaving a red check nobody is watching. It is a separate workflow file rather than a job added to `ci.yml`, since `ci.yml`'s aggregate `gate` check statically requires every job in that file to succeed and a job that only runs on push would read as "skipped" (and therefore red) on every pull request; a new test asserts its test matrix and steps stay in lockstep with `ci.yml`'s own, and it is never referenced by, or able to affect, any required check.
- Replaced a fixed wall-clock sleep with a real await on the production settlement (`jobStore`'s own `resolveBirthIdentityForKill`) at the two remaining sites in the process-observer test family that still asserted a captured birth identity right after a hand-picked delay (`test/shutdown.test.ts` and `test/kill.test.ts`), matching every other call site in this same family. This replaces an arbitrary number with the production guarantee on its own merits; it is a separate, still-open question whether the intermittent `ubuntu-latest`/node-22 reds in this family have the same cause, and this change does not close that question either way. Two adjacent sites that call the production `kill()` handler directly (which already awaits the resolver internally) needed no change.
- Corrected two README sentences that overstated job retention - one in "How it works", one in "How it's different from what agents already have" - both said `status`/`output`/`tail` stay accurate for as long as the server is up, with no further qualification. That much is still true for a client that only ever polls those three tools, but `tasksAdapter.ts`'s `getTask` reclaims a job's whole record, not just some Tasks-specific view of it, the moment anything reads an already-finished job through `tasks/get`, `tasks/update`, or `tasks/cancel` at least 24 hours after it ended (all three share the same read path); a still-running job is never touched by this, at any age. Both sentences now say so instead of the unqualified claim.
- Two tests covering `captureBirthIdentityPosixAsync`'s aggregate-timeout behavior injected a fake clock whose
  `now()` read the filesystem (`fs.existsSync` on a fixture marker file written by a background subprocess) to
  decide when the simulated clock should jump forward. That made the clock itself racy: whether the check saw the
  marker in time depended on real subprocess scheduling, the same kind of timing the clock exists to eliminate, so
  the test could occasionally observe a real, correctly-classified production result and still fail because its
  own fixture's timing assumption didn't hold. Fixed by driving each clock from a plain in-process call counter
  instead - it returns a fixed value for the two `now()` calls that happen before the first observation attempt
  resolves, then the intended tight budget from the next call onward. A call counter cannot observe subprocess
  timing at all, so there is no window left to be small or large - the race is removed by construction, not just
  made rarer.
- Fixed two specific, real flakes in the process-observer test family (`test/kill.test.ts`/`test/run.test.ts`'s birth-identity and kill-time identity assertions), where the exact same commit could pass one CI run and fail the next. First: `run()`'s production spawn-time identity capture (`captureBirthIdentityPosixAsync`) fired a single, unretried `ps` observation immediately after spawn; on a contended host the freshly-forked child is not always yet visible to that first `ps` call, and that one transient miss permanently settled the job's identity as unavailable for its whole lifetime, with no further attempt ever made. Fixed by retrying a "not found" observation for up to 1000ms at a 20ms poll interval, governed by a retry budget that starts only once the first "not found" is actually observed. A genuine observer failure (the `ps` call itself timing out) is never retried, since it has already exhausted its own timeout budget once. The retry addition preserves the pre-existing total-settlement bound `kill()` and the shutdown reaper both depend on: each retry's own observer timeout is capped by whatever remains of that bound, so a retry can never itself run past it - an observer still active when that bound expires is force-reaped and the capture settles unavailable, while a retry that started in time may still have its result honored even if it settles after its own retry window, since the settlement bound (not the retry window) is what actually protects `kill()`/shutdown from an unbounded wait. Two other observer-failure residuals in this same family - in `readPidStartTimesBatchPosix` and `captureEscalationIdentitySnapshot`, both pre-existing functions this change does not touch - remain unfixed and are disclosed rather than silently implied to be covered.
- Second: the test suite's own server-under-test spawn helper (`test/helpers/spawnServer.ts`) now gives the spawned server its own POSIX process group at spawn time, mirroring the containment every real job spawn already had. Previously the spawned server inherited whatever process group its caller belonged to; under a non-interactive shell invocation that group is the invoking shell's own, so an external process-group-scoped termination of "the whole test run" could kill the reviewing shell itself as collateral damage.
- `test/tools.test.ts`'s relative-PATH spawn test is not a member of either fix's affected population: its only real timing dependency is a generic filesystem-content poll waiting for a trivial script to finish writing a marker file, with no `ps`/`pgrep` observation or process-identity comparison anywhere in what it asserts.
- A repetition proof of `test/run.test.ts`, `test/process.test.ts`, and `test/kill.test.ts` found no recurrence of either fix's own original failure.
- Third: `test/run.test.ts` itself was carrying the same timing-assumption class the rest of this family was fixed for - its own `waitFor` helper polled a real, still-in-flight birth-identity capture against a hardcoded 5,000ms wall-clock deadline. That deadline is unrelated to the capture's own settlement guarantee (a hard, self-timed aggregate budget below 5,000ms with generous headroom under ordinary conditions) and can be exceeded by nothing worse than real CI scheduling delay for the underlying `ps` observation, producing a false timeout on an otherwise-correct capture. Fixed by replacing the wall-clock poll with a direct await on `jobStore`'s own `resolveBirthIdentityForKill` - the same real promise `kill()` and the shutdown reaper already await for this exact purpose - so the wait resolves exactly when the real capture settles, with no independent deadline of its own to race against it.

A task's id is the same id its backing job already uses, so there is exactly one identifier for a job whether a client is polling it the old way or through a minted handle. `tasks/update` and `tasks/cancel` currently return the task's current state without altering anything (`tasks/cancel`'s real cancellation behavior is coming in a follow-up); an unknown task id gets one consistent not-found response from all three methods.

- `kill()` now signals a job's whole POSIX process group instead of only the tracked leader: SIGTERM, a bounded grace period, then SIGKILL if anything in the group is still alive. A caller-supplied signal other than `SIGTERM` is sent exactly once, with no automatic escalation. That grace period carries a disclosed, unclosed residual: the group can fully empty during the wait and have its numeric id recycled by an unrelated later group before the pre-SIGKILL existence check that follows the wait actually runs, since existence alone cannot tell a survived original group apart from a coincidentally-reused one - narrowed as far as an existence check can go, not closed. This also closes a gap where a job whose leader had already exited on its own (forking children without waiting on them) never got a reap attempt for whatever it left behind - both `kill()` and the shutdown reaper now still attempt a real, external group-level reap for a terminal job record.

Fixed by deriving merged position from each line's own real per-stream sequence number instead.
- `kill()`'s escalation logic confirmed only the process group's leader had died before deciding a plain `SIGTERM` had worked. A leader with no handler of its own dies immediately from `SIGTERM` even while a descendant elsewhere in the same group - one that ignores or is slower to respond to the identical signal - keeps running, so the result reported success with a real process it was asked to terminate still alive. Fixed by confirming the whole process group is dead, not just the leader, before reporting either signal's outcome.

All three are flagged at their acquisition site now, alongside the existing forbidden-global checks.

- This guard is a hop-bounded hygiene check, not a security boundary: a SECOND hop of alias/computed-member acquisition (`const g = globalThis; const h = g; h.eval(x)`, the same one hop further on a `process`-base alias, and on a variable-keyed `.constructor` access) is now a disclosed, intentionally open route, confirmed to both stay unflagged and to genuinely execute the capability it reaches. Closing it would only move the same boundary out to a third hop, which this guard's scope explicitly does not chase; the regression suite now carries all three as tracked, evidenced open rows rather than leaving them to be rediscovered later.
- A doc comment describing this guard's acquisition-site design read as though the `globalThis`-qualified reaching of a forbidden global tolerated the same unlimited alias-hop count the bare-identifier form genuinely does; the two are different mechanisms with different bounds, and only the bare-identifier one is unlimited (it is caught at the first reference to the name itself, so no hop count matters). Split the two claims apart so each states its own real boundary.
- A benign, already-observed macOS shutdown race printed a false process-group kill error: a job's process group can exit in the narrow window between the shutdown handler's own liveness check and the actual signal send, and the signal call then reports `EPERM` rather than the already-handled `ESRCH` for this exact case. A second `kill(pid, 0)` probe cannot tell the two apart, since it is subject to the identical ambiguity - fixed by checking a real, external `pgrep -g` survivor count specifically for this `EPERM` case; any other signal-send failure still surfaces unconditionally, unchanged.
- Closed a TOCTOU race in the relative-`PATH` `run()` test's marker-file wait: it polled `fs.existsSync` alone, which can return `true` the instant the fixture script's shell redirect opens the file and before "ran" is actually flushed to it, so an unlucky follow-up read occasionally saw an empty file and failed a test whose code under test had worked correctly. Every other test file that waits on a marker file already avoids this with a shared `waitForFile` helper that polls for the expected content, not mere existence; this test now uses it too instead of its own bespoke existence loop.
- A child killed by a signal it never requested through `kill` (an external signal, a crash) used to come out `exited` instead of `killed`; `markExited` now splits on whether the OS actually reported a signal, and `JobDiagnostic.reason` is a closed three-value type instead of an open string. `output`/`tail`'s "both" stream used to number each line by its own per-stream position and stitch the two streams together with a synthetic odd/even guess; stdout and stderr now draw their sequence number from one counter shared per job, so merging is just sorting by that real value.
- An earlier attempt at this fix tried to disclose the EXACT dropped seq range a stream lost once it started evicting old lines under its retention cap. That kept fabricating: once stdout and stderr share one sequence counter, the seq values between a stream's own retained lines can legitimately belong to the OTHER stream and still be sitting there, untouched, so a single boundary (or a coalesced set of ranges) could wrongly claim a still-live sibling event as this stream's own loss. Rather than keep chasing an exact-but-fabrication-prone shape, `output`/`tail` now disclose a much simpler, bounded, and honest pair per stream once it has dropped anything: `dropped` (how many of that stream's own lines are gone for good) and `droppedBeforeCursor` (the boundary before which that happened) - never which specific lines were lost, so it can never misattribute a value that was never its own. Exact per-line gap-range disclosure is deferred to a follow-up.
- `truncated: true` used to reflect only a stream's own lifetime retention loss. It now also fires when a call's own `limit` (`output`) or `lines` (`tail`) left more already-available events undisclosed this time, a distinct cause from genuinely losing history - previously a caller could get back fewer events than existed with no signal that anything was left on the table.
- A single oversized line (one that alone exceeds the 1 MiB per-stream byte cap) is deliberately kept whole rather than evicted the instant it's created - but that exception stayed in force forever afterward too, so a further stream of newline-free data landing behind it could grow completely unbounded on top of it, well past the nominal cap, with nothing disclosed. Fixed: the exception now protects the oversized entry only for the append call that creates it - the moment a later, separate call brings in more data with no new line completing, that entry is evicted like any other, honestly counted in `dropped` and `truncated`.
- Added a real stdio-client test proving `kill()`'s default grace-period-then-SIGKILL escalation genuinely reaches a job whose own leader process ignores SIGTERM while its own forked descendants stay plainly killable (genuinely leader-only resistance, not group-wide): starting right after the kill() request is dispatched (written to the wire), the test polls the real process group until every original descendant's own pid is confirmed gone (or a safety deadline elapses), then confirms the leader and its keep-alive job are still alive at that point, closing a gap where the same test previously passed even with the leader-only behavior reverted to the old, group-wide bug. The escalated signal is confirmed both by a separate, follow-up `status()` call and by an external process-group check that the whole tree - the resistant leader and every child it forked - is actually gone afterward. Real kill() calls on three ordinary jobs are dispatched alongside the resistant kill and confirmed, by read-back timestamp, to have been read by the client well before the resistant leader's ~5-second escalation resolved; real status/output reads on those same jobs are confirmed to have been read before it too. The test reaps its own real process groups in a `finally` block regardless of where an assertion fails, so a mid-test failure can never orphan the real job trees it built.
- The module-loader guard that forbids referencing the MCP spec's in-progress "Tasks" extension checked for a subpath of a package this project has never installed, so nothing it named was actually reachable to begin with: importing the real Tasks symbols straight off the installed SDK's server package went entirely unflagged. Rewritten to check by SYMBOL instead of by module path, against this enumerated, closed set of reference forms: a plain/type-only import, a named/aliased/wildcard/namespace/type-only-namespace re-export, a value/type-position namespace member access, a type-import query, and a literal-root dynamic-import destructure (or an immediate property access off the awaited result). Matching is on the symbol's real exported name, never a local alias, and a computed reference the guard cannot statically resolve (a namespace member key, a dynamic-import specifier, a `require` specifier) is rejected rather than silently passed through, each its own diagnostic. The guarded symbol set is a hand-copied constant, checked against the installed package's real type declarations by a test that independently re-derives the set and fails on any drift - not derived by the guard itself at runtime. Specifier resolution follows real package identity so an aliased or differently-built reference to the same installed package is judged the same as the plain import.
- `npm run lint` now targets this project's own source directories (`src`, `scripts`, `test`, `eslint.config.js`) instead of the whole working tree.
- Birth-identity comparison for `kill()`'s PID-reuse check is now a real OS-observed elapsed-age reading (`ps -o etime=`), captured once right after a real spawn and compared against a fresh read at kill time - not a bare wall-clock timestamp. Capture runs asynchronously and is never awaited on `run()`'s own response path, so a slow or hung `ps` can't delay it; a job is tracked and killable immediately, with its identity honestly disclosed as `pending`, `captured`, or `unavailable` via a new `identity_capture` field. `kill()`/the shutdown reaper await the same in-flight capture, bounded by its own timeout, when one is still pending at the moment they need it. An observer failure (`ps`/`pgrep` unavailable or erroring) is a distinct, disclosed outcome, never confused with "process not found" or a false success.
- `kill_confirmed`/`identity_confirmed` now report exactly what a real, external `pgrep`-based process-group check actually observed - never a whole-tree or zero-surviving-descendants guarantee, since a descendant that escaped the group (via `setsid()`, for instance) is invisible to it. On the default path (no `signal` argument, or an explicit `SIGTERM`), the job's own `killed` state is synchronous and independent of this confirmation. A caller-supplied signal other than `SIGTERM` is different: a non-terminating one (`SIGSTOP`, for instance) only reaches `killed` once confirmation actually lands, and the job stays reachable for a follow-up `kill()` until then; a terminating one (an explicit `SIGKILL`) can independently reach `killed` via the process's own real exit before confirmation resolves, while both fields stay absent - never `false` - until it does. `kill()` and the shutdown reaper still attempt this same group-level check for an already-terminal job record whose leader exited on its own, so descendants a leader left behind still get reaped.
- Added real, spawned-process test coverage for all of the above: the identity check's fail-closed behavior at both real call sites, a literal `output`/`tail`-after-kill assertion, a real stdio-client test for leader-only escalation resistance (the leader ignores `SIGTERM` while its own descendants stay killable), a terminal record whose process group has already fully exited by the time a follow-up `kill()` reaches it (a genuine no-op: no signal reaches a live process, the record's state is unchanged, and the group's `ESRCH` response is the expected way absence is discovered), and a real escaped-descendant regression proving the process-group boundary is honestly disclosed rather than overclaimed. The terminal-record test reaps its own spawned processes in a `finally` regardless of where an assertion fails, with a standalone regression proving that cleanup pattern holds even when the code above it throws.
- A terminal job's own cleanup reap for descendants an already-exited leader left behind only ever sets `kill_confirmed`, never `identity_confirmed`, since that reap never re-runs the leader identity check at all.
- That cleanup reap now runs automatically the instant a job's leader is observed to have exited, rather than waiting for a caller to call `kill()` on the resulting terminal record. While the group still holds a member, the OS cannot recycle its id, so a group with surviving descendants is still provably the one this server spawned at the moment the exit is observed - but that continuity only holds until the last member leaves; where the leader has no surviving descendants, it IS the last member, so the group empties at exactly that exit, and no continuity carries through to this server's own callback. At most one signal-capable reap is attempted per job; a later `kill()`/shutdown against an already-reaped record may still re-check existence, but sends no further signal, so it can never itself land on a reused id. The remaining exposure - the gap between the group emptying and this server's own callback actually running - is disclosed honestly as normally very short but with no fixed upper bound, rather than a wall-clock tolerance it can't back up. `kill_confirmed` reports a STATE (the process group was observed to hold no members), never an ACTION (that a kill was performed) - it can be `true` on a job that simply exited on its own and was never signaled at all.
- Before escalating a `kill()`'s grace-period SIGTERM to SIGKILL, ghantika now checks whether the process group is still the one it spawned: it snapshots the leader plus every currently-live descendant's pid and real, `ps`-read start time right before the SIGTERM is sent, then, once the group survives the grace period, boundedly re-reads only those same recorded members. If any one of them still reports an exactly matching start time the escalation proceeds against the whole group as before; if none matches, escalation is refused and no SIGKILL is sent, disclosed via a new `escalation_refused_reason` field. This is a bounded, conservative check, not a proof: the number of real observations it makes never scales with group size (one batched `ps` read covers however many pids the group has, rather than one call per pid), though that one read still constructs, emits, and parses data proportional to the group's own size, and force-reaps an unresponsive `ps`/`pgrep` rather than leaving it running. This materially narrows, but does not close, the residual already disclosed above between "still alive" and "about to send SIGKILL" - the identity check and the SIGKILL itself remain two separate syscalls. A failed or degraded observation (a timeout, malformed output, or zero usable records) always refuses escalation rather than defaulting to it; the SIGTERM already sent is never held back by an observation failure, and is honestly disclosed as an unconfirmed best-effort send when neither this check nor the earlier pre-signal identity check could confirm anything.

- `run()` now accepts an optional `deadline_ms`: if the job is still running once that many milliseconds have elapsed, it is terminated through the exact same real process-group kill machinery `kill()` already uses (the pre-signal identity check, then the real SIGTERM/grace-period/SIGKILL escalation on POSIX, or the taskkill-based fallback on Windows), and the job is recorded `failed` with the same closed diagnostic-reason shape every other failed job already carries - never a new job status. The deadline transition itself does not delete the record, and it is present immediately after the deadline failure; ordinary task TTL can later purge that terminal record on a subsequent read, exactly as it can for any other terminal job. - Extended the `io.modelcontextprotocol/tasks` adapter so a backgrounded task stays observable for its whole life, not only at start and end. A still-running task now reports a stable `working` status across repeated reads rather than only a start/end snapshot; a completed task's record is removed on the next task read once it ages past a fixed TTL while a still-running task of any age is left untouched; and each new stdout batch wakes a capable client with exactly that batch's new lines, coalesced into one notification per short time window instead of firing once per line or only once at the end. A stream producing output faster than a bounded rate has its own wake notifications throttled and then stopped automatically - the underlying job keeps running and stays reachable by ordinary polling regardless, since the wake is deliberately only an accelerator on top of the existing poll surface, never a replacement for it: `tasks/get`, `output`, and `tail` behave identically whether or not a client listens for the wake at all. Underneath, `jobStore` gained two small generic hooks - one for a job's output as it is produced, one for the moment its state goes terminal - so an interested listener can subscribe to either without `jobStore` knowing anything about Tasks itself; each task's wake logic rides on its own per-task closures over those two subscriptions, while `jobStore` itself holds the persistent listener registrations and the watch-stop annotation for the life of the job record.

- `kill()`'s birth-identity comparison is now platform-specific rather than one shared etime-based reading everywhere, closing a real class of bug instead of one instance of it. `ps -o etime=` does not read an elapsed time; it computes one from `/proc/<pid>/stat`'s own `starttime` field converted against the system's current uptime, and in a virtualized guest those two values can come from mismatched sources, so a real, correctly-executing `ps` observation can still report a wildly wrong elapsed-time reading. The exact numeric mechanism behind one such observation was not confirmed. On Linux, the identity check now reads `/proc/<pid>/stat` field 22 (`starttime`, a raw kernel counter in clock ticks since boot) directly and compares it for exact string equality against the value captured at spawn - no unit conversion and no elapsed-time derivation at all, so the whole family of boot-time/uptime-conversion bugs is structurally impossible on this path rather than merely rarer. macOS is unchanged: it still compares a real, `ps`-observed elapsed-age reading within a tolerance window, since macOS has no `/proc` filesystem and its own `ps -o etime=` computation carries no equivalent virtualized-guest/uptime hazard. The Linux `/proc/<pid>/stat` read is now also bounded by the same effective timeout the non-Linux path already honored: an earlier version of this fix left the read as a plain, unbounded `await`; it now races against an independent caller-side timer, forcing settlement at the timeout regardless of whether the underlying read itself ever settles.

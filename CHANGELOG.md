# Changelog

All notable changes to this project are documented in this file.

## [Unreleased]

- The coverage job now emits the same JUnit-backed annotation the test job already did, so a test that fails only under coverage shows up on the PR's Checks tab instead of only in a raw log. The `changelog-presence` check's three commands (fetch, merge-base, the CHANGELOG diff itself) each now say which one failed rather than leaving a bare exit code as the only signal, on both the hosted check and its local mirror. Diagnosed a rare hosted-only JUnit-parsing failure in the third-party annotation action to a content-triggered bug in one of its own dependencies rather than anything in this repo, and recorded why it is left as a known, already-red-failing residual instead of chased further. Audited every top-level gate script for one that nothing wires in - the one already found (a required-consumers parity checker) turned out to have been fixed by later work; no new instance was found in this sweep.
- Corrected three code comments that claimed `c8` forces the test runner to a single concurrent file under coverage. Reading `c8`'s own source shows it has no such mechanism - it only sets `NODE_V8_COVERAGE` and spawns the wrapped command as one child process, with no inspection of what that command does internally. The actual reason a coverage run executes serially is that the `coverage` npm script never passes `--test-concurrency` to `node:test`'s `run()`, which defaults to serial when that flag is absent - the same reason any invocation without the flag is serial, coverage or not.
- `nextLine()`'s non-coverage wait was an unmeasured 2000ms while the coverage path carried a measured 6000ms; raised the non-coverage default to match, backed by a 14-run campaign at loaded concurrency (worst observed wait 653ms). Also replaced 21 fixed `setTimeout` delays across 6 test files with bounded polls on the actual observable state (job state, live process-group membership, an on-disk field) - a guessed delay under host contention produces a flaky failure unrelated to the code under test, a poll on the real signal does not.
- Added a poll-loop detector for a state that finishes entirely outside this process's own tree, with a GitHub Actions run reaching a terminal state as the concrete checker shipped alongside it. On firing, it wakes the target seat directly through the real wake-transport selector already used for a job's own completion - no doorbell file, no handoff to a separate watcher process. The whole poll-loop process group is reaped on every path (a fire, a detection failure, or an explicit stop), and a detection failure resolves as its own distinct outcome rather than reading like nothing happened.
- Added a generic, nonce-correlated ownership handoff (`scripts/lib/doorbell-cutover.mjs`) between two independently-armed wake detectors, plus two concrete detectors (`scripts/lib/doorbell-cutover-detectors.mjs`) - a bounded-interval poller and an fs.watch-based watcher - and a synthetic proof harness (`scripts/doorbell-cutover-harness.mjs`) that runs an initial cutover, twenty fixed steady-state cycles, a reverse cutover, and a final reap against a scratch trigger file. A successful cutover arms the target and confirms it with a real self-test before disarming the source, tolerating a brief window where both are genuinely armed rather than risking a gap where neither is watching; a failed cutover rolls back in the opposite order. Retries are bounded by both a count and a wall-clock deadline; every wake is classified as a resumption, a dedupe within a 120 second window, a reported late duplicate outside it, or spurious. Building the two detectors surfaced and fixed two real platform behaviors: a write issued with no delay immediately after `fs.watch()` construction can miss the underlying kernel-level watch registration entirely, and a write issued essentially simultaneously with an already in-flight watch callback can be coalesced away with no separate notification of its own.
- A coverage run that gets force-terminated by the idle watchdog or the wall-clock cap now voids the coverage-floor comparison instead of letting it run against a partial table. `c8` honestly reports whatever coverage it collected up to the point a run was cut off, and that partial table reads exactly like a real, complete run's, which could otherwise be reported as an ordinary coverage regression. `scripts/run-tests.mjs` now records why it terminated early, synchronously, right before exiting; `scripts/check-coverage-floor.mjs` reads that record first and refuses to compare when one is present, exiting a distinct code reserved for that state rather than reporting either an ordinary pass or an ordinary fail. Any consumer of this repo's own test-run records can read the same signal as an additive field alongside the ordinary pass/fail count. Also closes an orphan-cleanup gap for the one call site that spawns a nested test supervisor: on POSIX platforms (Linux, macOS) it now sweeps its whole process group afterward, so a stubborn grandchild process can no longer survive a signal sent only to its immediate parent there; on Windows the sweep is a no-op - there is no process-group signalling primitive to sweep with - so that same gap remains open on that platform.
- The truncation record above now survives a write failure to its own directory. If the primary location can't be written to, a second attempt lands at a fallback path outside it, and the floor check reads both locations before ever concluding a run completed cleanly. Without this, a directory that turned unwritable partway through - a sandboxed step, a permissions probe - left the record nowhere at all, and an idle-watchdog or wall-cap termination in that state read as an ordinary complete run instead of voiding.
- Added a crash-safe mutual-exclusion lock (`scripts/lib/coverage-floor-lock.mjs`) coordinating `npm run coverage` and `npm run check:coverage-floor`, which write to a set of shared files (`coverage/coverage-summary.json`, the run-truncated/run-completed markers, `.run-token.json`) with nothing today stopping two genuinely concurrent invocations of that pipeline from racing on them. Two thin wrapper scripts spawn the real commands under the lock without changing either one's inputs, outputs, or exit codes. A dead prior owner is reclaimable rather than a permanent deadlock - liveness is answered by asking the real OS whether the recorded pid is still alive and still the same process that wrote the record, never a bare pid, which can be silently reused - and any failure past the point a child was spawned kills that child and releases the lock before doing anything else, so a doomed owner can never block a later reclaim. The lock's own safety currently rests on a disclosed fact rather than purely on its own mechanics: this repo's CI runs the two wrapped commands as two strictly sequential steps in one job, never in parallel. A residual check-then-act window between each acquisition path's liveness check and its subsequent write/spawn is documented in the module's own header, along with what closing it for a genuinely concurrent shape would need.
- Added a temporary workflow that sweeps file concurrency on ubuntu-latest and macos-latest to measure a safe value for each, ahead of a later change that puts the measured value to use. It runs on push to its own branch, reports which concurrency values stay clean, and is removed once that follow-up change lands.
- Corrected a comment in the CI configuration that understated which checks branch protection actually requires.
- Local test runs can now opt into bounded file concurrency instead of running one file at a time, cutting a direct suite run's wall-clock time by roughly two-thirds on this host with no change in coverage. CI stays serial; this is a local-only, opt-in speedup for the plain suite run, not the coverage-bound gate.
- Fixed the batched process-identity read treating a single transient not-found observation as a final, confident result instead of retrying, closing an asymmetry with the single-pid read, which already retried.
- Added a new wake route for Claude Code that needs no environment variable set: ghantika reads the private messaging socket and credential the client already exports into its own subprocess's environment, and writes to it directly once a job that same session started reaches a terminal state. It reaches exactly the session that spawned ghantika, by construction, never anywhere else; it sits off the critical path of every other tool this server offers, and falls through cleanly wherever it is unavailable. `GHANTIKA_DISABLE_CLAUDE_MESSAGING_WAKE=1` opts out. End-to-end delivery through this route has not yet been observed; see `docs/wake-support-matrix.md`.
- Corrected several public-prose claims that stated or implied a wake replaces the need to poll, when the poll surface (`status`/`output`/`tail`) is always authoritative and every wake is only ever an accelerator on top of it: five README sentences either dropped a trailing "instead of asking" clause or, in one case, reconstructed the same claim in different words ("follow a job rather than poll it ... instead of holding the agent's turn open") and were reworded to state only what has actually been observed, with "can" replacing an unconditional "delivers" since the very next paragraph discloses a fresh-session case where it did not. A CHANGELOG entry no longer describes the desktop-IPC transport as waking a conversation when only its wire framing, not delivery through this server's own wake logic, has been confirmed. The wake support matrix gained a row for the Tasks-extension notification against Claude Code (a measured `did-not-work`, already recorded in the README but missing from the one document meant to hold every such result) and a note that the first `follow` call past the threshold in a fresh session was observed not to background. Added `scripts/check-wake-claim.mjs`, guarding the "instead of asking" claim shape the same way `scripts/check-polling-claim.mjs` already guards the universal-polling claim.
- Wired file concurrency into the coverage job itself rather than leaving it a local-only opt-in: the test runner now splits its file list into two batches and runs them as two separate `node:test` runs, one file at a time for whichever file is named in a small exclusion list, the rest concurrently at whatever value is passed. One file needed excluding - its own nested test-supervisor spawn is close enough to its fixed time bound that contention from other files running at the same time can push it over. What concurrency value the remaining batch should actually run at is not yet settled: a sweep of 2, 3, and 4, three repeats each, on this job's own hardware found none of them clean across every repeat, and surfaced two more contention-sensitive files beyond the one already excluded - the value currently wired is disclosed as unresolved rather than presented as validated. This widens the excluded file's own timing margin; it does not fix why a single marginal timeout there escalates into every later attempt at the same spawn repeating the identical, already-losing bet rather than failing fast - that gap is tracked as its own open item, not treated as resolved here.
- Settled the coverage job's file concurrency at 3. Two of the three contention-sensitive tests from the earlier sweep turned out to be bare timing bounds racing real load rather than proving anything about timing, and widening them was a free fix; a confirming re-sweep on the same instrument, same repeat count, found both clean across every repeat at 2 and at 3. 4 was tested and rejected: still one failure in three, for roughly 8% less wall-clock than 3 - not worth a gate that reds on one run in three unrelated to the change under review. The re-sweep's one remaining failure, at 4, surfaced a diagnosability gap of the same shape already fixed for the coverage job's public reporting: a repeat that failed with two tests reported no failing-test names at all, because `node:test`'s own spec reporter never emits the TAP-style lines a naive grep looks for - the actual names and assertions live only in its own end-of-run summary block. Tracked as its own open item, not fixed here.

### Added

- **`follow`, a seventh tool for a bounded wait on a job's next event**: new output on a chosen stream, the job reaching a terminal state, or an explicit `timeout_ms` (default 45000ms, capped at one hour), whichever comes first. A timeout is a normal, non-error result; `status`, `output`, and `tail` remain the way to check a job regardless of whether `follow` is ever called. The server caps outstanding `follow` calls at 128 across every connection it serves; a call made once that cap is reached is rejected immediately rather than queued. Cancelling the underlying MCP call tears down its subscription and any held slot right away, including for a client whose `tools/call` request carries an id of `0` or an empty string, a case the installed SDK's own cancellation dispatch otherwise misses.
- **A wake transport layer for resuming an idle agent session**, distinct from the plain poll surface: a `WakeTransport` contract (`probe()`/`wake()`, with delivered, refused, and unavailable as three separate outcomes) backs two concrete transports, tried in order with a refused, unavailable, or thrown attempt on one falling through to the next rather than stopping there, and stopping only at the first delivery. One wakes an idle Codex thread by spawning `codex app-server` and driving its documented JSON-RPC protocol; the other reaches a Codex conversation open in the ChatGPT desktop app over that app's own local IPC socket, the wire framing confirmed against a real session but end-to-end delivery through it not yet observed. `docs/wake-support-matrix.md` documents what has actually been observed for each route, including Claude Code's own client-side auto-background of a held `follow` call: the setup each needs, the real limits of each, how to reproduce the result, and that a first `follow` call in a brand-new session may not background. The poll floor (`status`, `output`, and `tail` answering any initialized client, no wake-specific setup required) is unaffected either way, and is stated up front so nothing in the matrix reads as a requirement for correctness. The mechanism ships inert by default, gated behind `GHANTIKA_WAKE_TRANSPORT_ENABLED`, a server-side environment variable no client can set over the wire.
- **Tasks extension support (`io.modelcontextprotocol/tasks`)**. The server advertises the capability, and `run()` returns a task handle instead of the plain `{job_id}` reply whenever a Tasks-capable call actually creates a job; a call the concurrency cap rejects creates no job and returns its ordinary rejection unchanged, regardless of capability. For a legacy connection, capability is a one-time declaration at `initialize` covering every call for that connection's life; for a connection served under the MCP 2026-07-28 revision, which has no `initialize` exchange to declare anything in, capability is read from each individual `tools/call` request's own metadata instead, so only that one call is governed by it. Every other tool, and the plain poll surface, stay byte-identical on every connection regardless of capability. `tasks/get`, `tasks/update`, and `tasks/cancel` are implemented against the extension's released 2026-07-28 contract; only the `extensions` bag that contract specifies is honored, not the SDK's own deprecated pre-2026-07-28 declaration. A capable client also receives a notification on a task's terminal transition and a coalesced wake on new output, both strictly additive to the existing poll surface. The extension's result schema is vendored in-repo with a recorded upstream commit and digest, and every deliberate divergence from that upstream source is enumerated and reasoned in `config/tasks-schema-provenance.json`.
- **A concurrency cap and bounded admission queue in front of `run()`'s spawn.** A job arriving while the cap is full and the queue has room reports `starting` with a new `queue_position` field; one arriving once both are full is rejected immediately, with no job ever created. `run()` never waits for admission, spawn completion, or command execution before returning. A queued job's position is visible through `status` and `list`; `list` also reports the current cap.
- **Retention for a finished job's buffered output.** It becomes eligible for reclamation once `GHANTIKA_JOB_RETENTION_MS` milliseconds have elapsed since the job ended (default one hour) or the number of eligible finished jobs exceeds `GHANTIKA_MAX_RETAINED_JOBS` (default 200), whichever comes first. A still-running job's output, and a job's own record (`status`/`list`), are never touched by this. `output`/`tail` disclose reclaimed content the same honest way they already disclose an ordinary byte or line-cap eviction, never a bare not-found that would read identically to a job id that never existed.
- **A command allowlist policy.** For an argv-array job, `run` checks the command's fully resolved executable path (PATH lookup, symlinks followed) against an operator-configured allowlist, loaded from a JSON file named by the `GHANTIKA_POLICY_FILE` environment variable, before it ever spawns anything. For a shell-string job, that same allowlist instead gates the fixed, resolved platform shell binary (`/bin/sh` on POSIX, the resolved `ComSpec` on Windows) that will run the string; the string's own contents play no part in the decision. The default with nothing configured is to deny every command. A denied command settles as a failed job immediately, with a diagnostic naming the denial, and never reaches the real process spawn.
- **`GHANTIKA_CWD_ROOTS`**, scoping `run` to an operator-configured set of allowed working directories. A candidate `cwd` is compared against each configured root by its real, symlink-resolved target, never a literal string prefix, so a directory reachable only through a symlink is judged by where it actually points.
- **An optional `deadline_ms` on `run`.** A job still running once that many milliseconds have elapsed is terminated and settles `failed` with the same closed diagnostic-reason shape every other failed job carries. On POSIX this termination is, in the ordinary case, gated on the same pre-signal identity check `kill()` itself applies: when the check cannot safely proceed (the process is already gone, or a genuine identity mismatch), the deadline refuses to signal rather than terminate an unrelated process, and the job's real outcome is recorded by whatever already-in-flight event explains it. On Windows there is no equivalent identity check on this path; the deadline terminates the process tree directly. Omitting the field leaves a job's behavior completely unchanged.
- **Public CI on GitHub-hosted runners**: build, typecheck, lint, and an operating-system by Node-version test matrix, plus CodeQL, semgrep, zizmor, and actionlint, all aggregated behind one required `gate` check, alongside a blocking Prettier format check and a coverage job with an absolute per-metric floor. A separate `Main Verify` workflow runs the same matrix on every push to `main`, so a defect that lands there is caught even between pull requests.
- **Process identity reporting on `status`.** A `pid` field reports the OS process a job was tracked against, once it ever had one, always alongside a `birth_identity` state (`pending`, `captured`, or `unavailable`), so a stale-looking pid can be verified against a real captured identity rather than trusted on its own.

### Changed

- **`kill()` signals a job's whole process group**, not only the tracked leader: SIGTERM, a bounded grace period, then SIGKILL if anything in the group is still alive. Before escalating a `kill()`'s grace-period SIGTERM to SIGKILL, ghantika checks whether the process group is still the one it spawned: a leader-plus-descendant identity snapshot taken right before the SIGTERM is compared, via one batched read, against a fresh read once the grace period ends; if none of the recorded members still shows a matching start time, escalation is refused and no SIGKILL is sent, disclosed via a new `escalation_refused_reason` field. This is a bounded, conservative check rather than a guarantee: a failed or degraded observation always refuses escalation instead of defaulting to it, and an unresponsive `ps`/`pgrep` is force-reaped rather than left running.
- **Birth-identity comparison is platform-specific.** On Linux, the tracked job leader's own birth identity is confirmed against `/proc/<pid>/stat`'s own raw kernel start-time counter, compared for exact equality with no unit conversion, closing a class of bug where a virtualized guest's clock sources could disagree under the elapsed-time computation `ps -o etime=` performs internally. On POSIX, a process group's other members are instead revalidated through one batched `ps` read of their own start times. macOS continues to compare the leader's own real, `ps`-observed elapsed-age reading within a tolerance window, since macOS has no equivalent `/proc` filesystem.
- **`kill_confirmed` and `identity_confirmed` report exactly what a real, external check observed.** Each is a different kind of check (a `pgrep`-based process-group read for `kill_confirmed`, a birth-identity read of the tracked leader for `identity_confirmed`), and neither is a whole-tree guarantee: a descendant that escaped the process group is invisible to either. A job that never spawned a process group at all, including one cancelled while still queued or still queued at server shutdown, settles `kill_confirmed` to `true` vacuously, since its group trivially holds zero members. Neither field is ever `false` while a real answer is still pending; a caller sees it simply absent until it settles.
- **`output` and `tail` disclose loss and truncation more precisely.** `dropped` counts every discrete loss event a stream has suffered, an evicted line, a discarded pending fragment, or a chunk that arrives after a job's output was already reclaimed, rather than only a materialized-line count, so sub-line loss is never silently invisible. `truncated: true` also fires when a call's own `limit` or `lines` argument left more already-available events undisclosed, distinct from genuinely losing history. The combined stdout-and-stderr view numbers events from one real, stable sequence counter shared per job, so a cursor from one call keeps matching the same lines on a later call that reuses the same stream selection, even after older lines have been evicted; switching stream selection can skip an already-retained event on the other stream, so a caller changing selection should restart from a fresh cursor rather than reuse one from a different selection.
- **A job's client-visible terminal state is ordered after its own last output event for `exited` from a normal exit, or `killed` from a signal the job received from outside this server**, whenever the reap that observed its process group empty is confirmed and no descendant has left the group: already-buffered output has fully drained, and any backgrounded grandchild inheriting the job's stdio has already closed it, by the time the terminal state becomes visible to a caller. A `kill()` this server itself performs is different by design: it claims the terminal state synchronously the instant the signal is sent, so a job it killed is never misreported as merely exited, and output the process writes while handling that signal can arrive after the terminal state is already visible.
- **The server serves the MCP 2026-07-28 revision's `server/discover` opening exchange alongside the existing legacy `initialize` handshake.** Which era a connection uses is decided once, at that connection's own opening exchange, and pins the rest of that connection's behavior for its lifetime; a client that falls back from an optimistic `server/discover` probe to `initialize` gets a fresh instance built the same way. The `-32700`/`-32600` error replies (unparseable JSON, or JSON that parses but fails the base JSON-RPC envelope) are produced ahead of the real transport, on a single raw-stdin classification shared by both eras rather than two separate mechanisms.
- **Tasks capability negotiation is era-specific.** A legacy, pre-2026-07-28 connection declares Tasks support once, at `initialize` time, for its whole lifetime. A connection served under the MCP 2026-07-28 revision has no `initialize` exchange to declare anything in; capability is read from each individual `tools/call` request's own metadata instead, so only that one call is governed by it, never the connection as a whole. On both eras, a client declaring Tasks support only through the SDK's deprecated `capabilities.tasks` field, the obsolete 2025-11-25 wire vocabulary, never has a task minted from that declaration.
- **The Tasks-extension notification layer uses the released contract's own wire vocabulary**, kept separate from ghantika's own output-delta wake. The output-delta wake, the coalesced per-batch stdout/stderr accelerator, now fires on stderr output the same way it already did on stdout, so a command that reports progress only on stderr gets the same accelerator a stdout-only command already got - on top of the same poll floor either way. It is sent under its own explicit, non-spec method name, `notifications/ghantika/outputWake`, so it cannot be mistaken for extension traffic. A spec-conformant `notifications/tasks` notification fires on every task's terminal transition, carrying the same complete task snapshot `tasks/get` would return at that instant, delivered to every Tasks-capable connection for a task it minted, since the installed SDK's own `subscriptions/listen` routing has no support for the extension's per-task-id filter.
- **Moved typechecking and building onto TypeScript 7** through a side-by-side compatibility layer: `typescript` resolves to a thin TypeScript 6 compatibility package (`npm:@typescript/typescript6@6.0.2`), while a separate `@typescript/native` entry carries the real 7.x compiler that `tsc`, `npm run build`, and `npm run typecheck` actually run against, the layout TypeScript's own 7.0 release describes for this situation. An editor's language service reads the `typescript` package, so it runs on 6.x even though the command line compiles with 7; `typescript-eslint`'s declared peer range still excludes TypeScript past 6.1, and this layout routes around that constraint rather than lifting it. The compatibility package resolves to 6.0.2, the highest version it publishes; it in turn pulls in real TypeScript 6.0.3, the newest release every one of `typescript-eslint`'s peer-declaring packages admits under their declared range.
- `npm test` and `npm run coverage` now run through `scripts/run-tests.mjs`, a custom test-file discovery and execution wrapper, in place of a shell glob.
- **CI's test matrix runs `ubuntu-latest` and `macos-latest`, each against Node 22 and 24.** There is no Windows CI signal right now, no hosted leg, no VM, no nightly substitute. The Windows-specific code paths (process-tree kill, executable-extension resolution) remain live production code with no CI coverage on that platform.
- **The module-loader guard matches a forbidden primitive at its acquisition site by real, resolved symbol identity rather than by invocation shape.** Every route to a small set of forbidden JavaScript primitives is flagged at its acquisition site, including three routes a specifier-string match cannot see: `createRequire` acquired via `process.getBuiltinModule`, the `Function` constructor reached via an ordinary function's own `.constructor`, and the global `eval` reached via `Reflect.get(globalThis, "eval")`. It is disclosed as a hop-bounded hygiene check rather than a security boundary: a second hop of alias or computed-member acquisition is an intentionally open, tracked route this guard does not chase, and the `node:module` import routes to `createRequire` still match by literal specifier text rather than resolved identity.
- `npm run lint` now targets this project's own source directories (`src`, `scripts`, `test`, `eslint.config.js`) instead of the whole working tree.
- **Dependency and security updates**: `js-yaml` (fixing GHSA-pm4m-ph32-ghv5, an exponential-time parse on crafted input; a devDependency-only exposure, since the shipped package has no runtime dependency on `js-yaml`), `typescript-eslint`, the CodeQL action, `eslint`, `globals`, `@types/node`, `actions/checkout`, `actions/setup-python`, and Prettier all carried forward to current releases, and the `@modelcontextprotocol` SDK bumped to its released 2.0.0 GA version. CI's pinned `semgrep` version is kept current the same way; `zizmor` is bumped because its prior pinned release was withdrawn by its own publisher.

### Fixed

- **A real race in `kill_confirmed`'s write path**: an external confirmation could be silently discarded when an eager reap at process exit resolved before the record's own terminal-state transition landed, permanently stranding the field rather than merely settling it late. The guard causing this is removed outright, since the field's own contract never depended on the record's state in the first place.
- **A false process-group kill error on macOS**: a job's process group can exit in the narrow window between the shutdown handler's own liveness check and the signal send; the signal call then reports `EPERM` rather than the already-handled `ESRCH` for this exact case, and it is now recognized rather than misreported as an unexpected error.
- **A transient birth-identity capture miss on a contended host**: a freshly-forked child is not always yet visible to the very first `ps` observation, and that single miss could permanently settle a job's identity as unavailable. The capture now retries a "not found" observation for up to 1000ms, bounded so a retry can never itself run past the total-settlement guarantee `kill()` and the shutdown reaper both depend on.
- **`README.md` states, in terms, where the Tasks-extension notification mechanism falls short of the released spec.** On a 2026-07-28-revision connection, only `tasks/update` currently dispatches; the revision's method registry has no entry yet for `tasks/get` or `tasks/cancel`, so a request naming either returns `-32601 Method not found` regardless of capability. The terminal-transition notification is sent unconditionally to the connection that minted a task, rather than following the released subscription protocol's per-client, task-id opt-in, since the installed SDK's own routing has no support for that filter.

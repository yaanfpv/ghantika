# Changelog

All notable changes to this project are documented in this file.

## [Unreleased]

- Pinned `typescript` to 6.0.3, the newest release that all eight of `typescript-eslint`'s relevant peer-declaring packages (the `typescript-eslint` meta-package and seven sub-packages: `@typescript-eslint/eslint-plugin`, `@typescript-eslint/parser`, `@typescript-eslint/project-service`, `@typescript-eslint/tsconfig-utils`, `@typescript-eslint/type-utils`, `@typescript-eslint/typescript-estree`, `@typescript-eslint/utils`) agree admit under their declared `>=4.8.4 <6.1.0` range, replacing the previous 5.9.3 pin. With no explicit `types` compiler option, 6.0.3 no longer auto-includes `@types/node`'s ambient globals the way 5.9.3 did: a controlled probe (removing `types` from `tsconfig.json` and re-running `tsc --noEmit`) emits 88 diagnostics across six files (`src/index.ts`, `src/jobStore.ts`, `src/process.ts`, `src/server.ts`, `src/tools/kill.ts`, `src/tools/run.ts`) - six missing `node:*` import specifiers, five missing ambient globals or namespaces (`process`, `Buffer`, `console`, the `NodeJS` namespace, `setTimeout`), and eight cascading diagnostics in two classes (seven implicit-`any` parameters, one `ImportMeta.url` property lookup). Fixed by declaring `"types": ["node"]` in `tsconfig.json` explicitly instead of leaving it implicit. A newer TypeScript exists upstream; adopting it now would fall outside `typescript-eslint`'s declared peer range, so it stays out of scope here. Two new guard scripts keep the constraint checkable rather than relying on memory: one reads all eight packages' installed `peerDependencies.typescript` entries directly and confirms the pinned version satisfies the agreed range - a genuine widening, if every package agrees on it, is followed rather than fought by this script; a companion test's own hardcoded assertion against the real installed range is what turns a future widening into a visible failing diff - the other confirms the open pull request tracking a newer TypeScript stays open and undeleted from `dependabot.yml`'s ignore list, since that open PR is the intended signal for when the peer range eventually widens.
- Bumped the pinned semgrep version used by CI from 1.170.0 to 1.171.0, since a newer release exists and the previous pin no longer matched the current rule engine. Re-running the newer version directly against this repo found the same 0 findings across the same 248 rules and 44 tracked files, so this catches the pin up to an already-verified-equivalent version rather than taking an unverified jump.
- Renamed the module-loader guard test's mutation-case fixtures and scratch directories to plain, descriptive names (an absolute-path scratch directory, a symlink scratch directory, a package-alias scratch directory, and fixture files named for the specifier form each one exercises) and rewrote a handful of comments to state the underlying technical fact directly; comments, names, and assertion failure messages read more plainly. Same 49 cases throughout, but two of the final restoration check's assertions changed from an existence check to a byte-content comparison against the two tracked guard files - a case that wrote to the tracked file instead of its own scratch copy is now caught, which the prior existence check could not do.
- Bumped `zizmor` from 1.27.0 to 1.28.0 in CI. The prior pinned release was withdrawn by its publisher on PyPI; the workflow-security linter should not run the one release its own maintainers pulled.
- The test runner now fails the whole run if a test gets silently skipped outside a checked-in per-platform baseline, if a critical test is skipped, disappears, or is left only as an unimplemented TODO stub, or if a duplicate test name would otherwise let a real skip get silently overwritten by a later, cleanly-passing completion of the same name - so none of those can quietly leave the suite reporting green. The production entrypoint reads no environment variable to redirect its test directory, baseline, or critical-test list; a throwaway fixture tree is exercised only through a separate test-only harness that takes those paths as ordinary function arguments, so the real check can no longer be pointed anywhere but this repo's own tracked files.
- Added `io.modelcontextprotocol/tasks` capability negotiation, behind a new thin adapter (`src/tasksAdapter.ts`) that sits over the existing job/output layer without either one importing from the other's shape. The server now advertises the capability in every `initialize` response; on a connection whose client also advertised it, `run()` hands back an unsolicited task handle instead of the plain `{job_id}` reply, while `status`/`output`/`tail`/`kill`/`list` are completely unchanged - a non-capable connection still gets the exact same byte-stable response `run()` has always returned, and the plain poll surface stays reachable on every connection regardless.
- Added the three `tasks/get`, `tasks/update`, and `tasks/cancel` methods. `tasks/get` reflects a task's real, live backing job - its evolving or terminal status, real exit code, and real output volume - never a canned placeholder. A task's id is the same id its backing job already uses, so there is exactly one identifier for a job whether a client is polling it the old way or through a minted handle. `tasks/update` and `tasks/cancel` currently return the task's current state without altering anything (`tasks/cancel`'s real cancellation behavior is coming in a follow-up); an unknown task id gets one consistent not-found response from all three methods.
- Vendored the Tasks extension's result schema in-repo (`schema/tasks-extension.schema.json`) with a recorded, enforced digest (`config/tasks-schema-digest.json`) rather than depending on an npm package for it - no such package exists on the registry. The SDK-pin guard now also fails if that file's bytes and its recorded digest ever disagree.
- `kill()` now signals a job's whole POSIX process group instead of only the tracked leader: SIGTERM, a bounded grace period, then SIGKILL if anything in the group is still alive. A caller-supplied signal other than `SIGTERM` is sent exactly once, with no automatic escalation. That grace period carries a disclosed, unclosed residual: the group can fully empty during the wait and have its numeric id recycled by an unrelated later group before the pre-SIGKILL existence check that follows the wait actually runs, since existence alone cannot tell a survived original group apart from a coincidentally-reused one - narrowed as far as an existence check can go, not closed. This also closes a gap where a job whose leader had already exited on its own (forking children without waiting on them) never got a reap attempt for whatever it left behind - both `kill()` and the shutdown reaper now still attempt a real, external group-level reap for a terminal job record.
- Added public CI on GitHub-hosted runners: build, typecheck, lint, and an operating-system by Node-version test matrix, plus CodeQL, semgrep, zizmor, and actionlint, all aggregated behind one required `gate` check.
- Added a blocking Prettier format check and a coverage job (an absolute per-metric floor, plus an informational delta against a checked-in baseline) to CI, both required by `gate`.
- Fixed the CI test job never building before running tests, added a `ghantika` executable via `bin`/shebang/`prepack`, and updated dependencies.
- Bumped `typescript-eslint` to 8.65.0 and the `@modelcontextprotocol` SDK packages to 2.0.0-beta.5.
- `output`/`tail`'s combined-stream mode numbered events relative to each caller's own transient array index rather than a real, stable sequence, so a cursor from one call stopped matching the same lines on the next once older lines had been evicted - a caller polling for new output could keep re-fetching the same window forever, with no way to reach an empty page. Fixed by deriving merged position from each line's own real per-stream sequence number instead.
- `kill()`'s escalation logic confirmed only the process group's leader had died before deciding a plain `SIGTERM` had worked. A leader with no handler of its own dies immediately from `SIGTERM` even while a descendant elsewhere in the same group - one that ignores or is slower to respond to the identical signal - keeps running, so the result reported success with a real process it was asked to terminate still alive. Fixed by confirming the whole process group is dead, not just the leader, before reporting either signal's outcome.
- Closed three more routes to a forbidden module-loader primitive: acquiring `createRequire` via `process.getBuiltinModule("node:module")` instead of an `import`/`require` of `node:module` directly, obtaining the `Function` constructor via any ordinary function's own `.constructor` property, and reaching the global `eval` via `Reflect.get(globalThis, "eval")`. All three are flagged at their acquisition site now, alongside the existing forbidden-global checks.
- Fixed the test suite hanging on Windows: added a 30-second per-test timeout and a 15-minute CI job timeout, and gave the handful of tests that exercise real POSIX process-group primitives (`pgrep`, `ps`, negative-pid signaling) a named skip on that platform instead of hanging indefinitely. Windows was a fully supported CI leg at the time this shipped; only these specific test-harness primitives lacked a Windows-equivalent path (see below for the leg's current, temporary removal).
- Replaced the `node --test '<glob>'` invocation behind `npm test`/`npm run coverage` with `scripts/run-tests.mjs`, which discovers test files itself instead of handing a glob to a shell (the glob was reaching `cmd.exe` unexpanded on Windows and silently running zero tests) and adds two separate diagnostics a per-test timeout can't produce on its own: an idle watchdog that names every file with no completion event of its own once nothing has happened for too long, without attributing a cause, plus a wall-clock cap for the whole run; and a distinct check for a run that finished normally and then failed to drain, a different failure shape than a file stalling mid-run.
- Removed a temporary Windows diagnostic workflow: its two timeout bounds were composed so its own pass condition could never be reached on any run, by construction, which made its intended product-file diagnosis uninterpretable. The real CI gate reproduces the underlying Windows test failures independently of it.
- Removed Windows from CI's test matrix for now: the `test` job runs `ubuntu-latest` and `macos-latest` only, each against Node 22 and 24. There is no Windows CI signal of any kind right now - no hosted leg, no VM, no nightly substitute.
- `windowsExtensionCandidates` (part of executable resolution) remains live production code but is now verified only by reading, not by execution, and the Windows process-tree kill path's own test degrades to shape-only coverage, both for the same reason: nothing exercises either against a real Windows host anymore.
- Hardened the workflow-matrix and gate-dependency guards: the gate-dependency guard derived its own expected required-job list from the same workflow file it checks (the matrix guard's expected axes were already independent literals), so shrinking the workflow and the guard's own expected-values constant together used to slip past unnoticed. Each guard now also carries an independent, hard-coded expectation living only in its test file, so shrinking the workflow and a guard's expected values together now also has to change a hard-coded list in the test file.
- `continue-on-error` detection now catches a quoted string or a GitHub Actions expression, not just the literal boolean `true`, since GitHub treats all three identically at runtime - including on the `gate` aggregate job itself, which is the one required check branch protection actually points at.
- The gate-dependency guard's literal-success check now parses the controlling expression into a small boolean tree and evaluates it with each job's own check forced false, rather than checking text adjacency around the matched literal - closing a class of disjunction bypass where extra operands separated the literal from the disjunction that actually governed it under real operator precedence.
- The matrix-completeness guard no longer crashes with an unrelated exception when its expected axes are degenerate (for example `null`); it now reports the same named diagnostic it always built, rather than that diagnostic being pre-empted by a crash before it could print.
- Added a real, executed regression suite for the module-loader guard's documented escape-route class (one-hop aliasing, computed/destructured `.constructor`, descriptor reads, casts, specifier resolution through absolute paths/`file://`/symlinks/package aliases/transitive barrels): every route runs against a real fixture tree through the guard's own production entry point, and the two guard-self-checks confirm the fail-closed and specifier-resolution logic are genuinely load-bearing, not vacuous.
- This guard is a hop-bounded hygiene check, not a security boundary: a SECOND hop of alias/computed-member acquisition (`const g = globalThis; const h = g; h.eval(x)`, the same one hop further on a `process`-base alias, and on a variable-keyed `.constructor` access) is now a disclosed, intentionally open route, confirmed to both stay unflagged and to genuinely execute the capability it reaches. Closing it would only move the same boundary out to a third hop, which this guard's scope explicitly does not chase; the regression suite now carries all three as tracked, evidenced open rows rather than leaving them to be rediscovered later.
- A doc comment describing this guard's acquisition-site design read as though the `globalThis`-qualified reaching of a forbidden global tolerated the same unlimited alias-hop count the bare-identifier form genuinely does; the two are different mechanisms with different bounds, and only the bare-identifier one is unlimited (it is caught at the first reference to the name itself, so no hop count matters). Split the two claims apart so each states its own real boundary.
- A benign, already-observed macOS shutdown race printed a false process-group kill error: a job's process group can exit in the narrow window between the shutdown handler's own liveness check and the actual signal send, and the signal call then reports `EPERM` rather than the already-handled `ESRCH` for this exact case. A second `kill(pid, 0)` probe cannot tell the two apart, since it is subject to the identical ambiguity - fixed by checking a real, external `pgrep -g` survivor count specifically for this `EPERM` case; any other signal-send failure still surfaces unconditionally, unchanged.
- Closed a TOCTOU race in the relative-`PATH` `run()` test's marker-file wait: it polled `fs.existsSync` alone, which can return `true` the instant the fixture script's shell redirect opens the file and before "ran" is actually flushed to it, so an unlucky follow-up read occasionally saw an empty file and failed a test whose code under test had worked correctly. Every other test file that waits on a marker file already avoids this with a shared `waitForFile` helper that polls for the expected content, not mere existence; this test now uses it too instead of its own bespoke existence loop.
- A child killed by a signal it never requested through `kill` (an external signal, a crash) used to come out `exited` instead of `killed`; `markExited` now splits on whether the OS actually reported a signal, and `JobDiagnostic.reason` is a closed three-value type instead of an open string. `output`/`tail`'s "both" stream used to number each line by its own per-stream position and stitch the two streams together with a synthetic odd/even guess; stdout and stderr now draw their sequence number from one counter shared per job, so merging is just sorting by that real value.
- An earlier attempt at this fix tried to disclose the EXACT dropped seq range a stream lost once it started evicting old lines under its retention cap. That kept fabricating: once stdout and stderr share one sequence counter, the seq values between a stream's own retained lines can legitimately belong to the OTHER stream and still be sitting there, untouched, so a single boundary (or a coalesced set of ranges) could wrongly claim a still-live sibling event as this stream's own loss. Rather than keep chasing an exact-but-fabrication-prone shape, `output`/`tail` now disclose a much simpler, bounded, and honest pair per stream once it has dropped anything: `dropped` (how many of that stream's own lines are gone for good) and `droppedBeforeCursor` (the boundary before which that happened) - never which specific lines were lost, so it can never misattribute a value that was never its own. Exact per-line gap-range disclosure is deferred to a follow-up.
- `truncated: true` used to reflect only a stream's own lifetime retention loss. It now also fires when a call's own `limit` (`output`) or `lines` (`tail`) left more already-available events undisclosed this time, a distinct cause from genuinely losing history - previously a caller could get back fewer events than existed with no signal that anything was left on the table.
- A single oversized line (one that alone exceeds the 1 MiB per-stream byte cap) is deliberately kept whole rather than evicted the instant it's created - but that exception stayed in force forever afterward too, so a further stream of newline-free data landing behind it could grow completely unbounded on top of it, well past the nominal cap, with nothing disclosed. Fixed: the exception now protects the oversized entry only for the append call that creates it - the moment a later, separate call brings in more data with no new line completing, that entry is evicted like any other, honestly counted in `dropped` and `truncated`.
- Added a real stdio-client test proving `kill()`'s default grace-period-then-SIGKILL escalation genuinely reaches a job whose own leader process ignores SIGTERM while its own forked descendants stay plainly killable (genuinely leader-only resistance, not group-wide): starting right after the kill() request is dispatched (written to the wire), the test polls the real process group until every original descendant's own pid is confirmed gone (or a safety deadline elapses), then confirms the leader and its keep-alive job are still alive at that point, closing a gap where the same test previously passed even with the leader-only behavior reverted to the old, group-wide bug. The escalated signal is confirmed both by a separate, follow-up `status()` call and by an external process-group check that the whole tree - the resistant leader and every child it forked - is actually gone afterward. Real kill() calls on three ordinary jobs are dispatched alongside the resistant kill and confirmed, by read-back timestamp, to have been read by the client well before the resistant leader's ~5-second escalation resolved; real status/output reads on those same jobs are confirmed to have been read before it too. The test reaps its own real process groups in a `finally` block regardless of where an assertion fails, so a mid-test failure can never orphan the real job trees it built.
- The module-loader guard that forbids referencing the MCP spec's in-progress "Tasks" extension checked for a subpath of a package this project has never installed, so nothing it named was actually reachable to begin with: importing the real Tasks symbols straight off the installed SDK's server package went entirely unflagged. Rewritten to check by SYMBOL instead of by module path, against this enumerated, closed set of reference forms: a plain/type-only import, a named/aliased/wildcard/namespace/type-only-namespace re-export, a value/type-position namespace member access, a type-import query, and a literal-root dynamic-import destructure (or an immediate property access off the awaited result). Matching is on the symbol's real exported name, never a local alias, and a computed reference the guard cannot statically resolve (a namespace member key, a dynamic-import specifier, a `require` specifier) is rejected rather than silently passed through, each its own diagnostic. The guarded symbol set is a hand-copied constant, checked against the installed package's real type declarations by a test that independently re-derives the set and fails on any drift - not derived by the guard itself at runtime. Specifier resolution follows real package identity so an aliased or differently-built reference to the same installed package is judged the same as the plain import.
- `npm run lint` now targets this project's own source directories (`src`, `scripts`, `test`, `eslint.config.js`) instead of the whole working tree.
- Birth-identity comparison for `kill()`'s PID-reuse check is now a real OS-observed elapsed-age reading (`ps -o etime=`), captured once right after a real spawn and compared against a fresh read at kill time - not a bare wall-clock timestamp. Capture runs asynchronously and is never awaited on `run()`'s own response path, so a slow or hung `ps` can't delay it; a job is tracked and killable immediately, with its identity honestly disclosed as `pending`, `captured`, or `unavailable` via a new `identity_capture` field. `kill()`/the shutdown reaper await the same in-flight capture, bounded by its own timeout, when one is still pending at the moment they need it. An observer failure (`ps`/`pgrep` unavailable or erroring) is a distinct, disclosed outcome, never confused with "process not found" or a false success.
- `kill_confirmed`/`identity_confirmed` now report exactly what a real, external `pgrep`-based process-group check actually observed - never a whole-tree or zero-surviving-descendants guarantee, since a descendant that escaped the group (via `setsid()`, for instance) is invisible to it. On the default path (no `signal` argument, or an explicit `SIGTERM`), the job's own `killed` state is synchronous and independent of this confirmation. A caller-supplied signal other than `SIGTERM` is different: a non-terminating one (`SIGSTOP`, for instance) only reaches `killed` once confirmation actually lands, and the job stays reachable for a follow-up `kill()` until then; a terminating one (an explicit `SIGKILL`) can independently reach `killed` via the process's own real exit before confirmation resolves, while both fields stay absent - never `false` - until it does. `kill()` and the shutdown reaper still attempt this same group-level check for an already-terminal job record whose leader exited on its own, so descendants a leader left behind still get reaped.
- Added real, spawned-process test coverage for all of the above: the identity check's fail-closed behavior at both real call sites, a literal `output`/`tail`-after-kill assertion, a real stdio-client test for leader-only escalation resistance (the leader ignores `SIGTERM` while its own descendants stay killable), a terminal record whose process group has already fully exited by the time a follow-up `kill()` reaches it (a genuine no-op: no signal reaches a live process, the record's state is unchanged, and the group's `ESRCH` response is the expected way absence is discovered), and a real escaped-descendant regression proving the process-group boundary is honestly disclosed rather than overclaimed. The terminal-record test reaps its own spawned processes in a `finally` regardless of where an assertion fails, with a standalone regression proving that cleanup pattern holds even when the code above it throws.
- A terminal job's own cleanup reap for descendants an already-exited leader left behind only ever sets `kill_confirmed`, never `identity_confirmed`, since that reap never re-runs the leader identity check at all.
- That cleanup reap now runs automatically the instant a job's leader is observed to have exited, rather than waiting for a caller to call `kill()` on the resulting terminal record. While the group still holds a member, the OS cannot recycle its id, so a group with surviving descendants is still provably the one this server spawned at the moment the exit is observed - but that continuity only holds until the last member leaves; where the leader has no surviving descendants, it IS the last member, so the group empties at exactly that exit, and no continuity carries through to this server's own callback. A reap is attempted at most once per job; a later `kill()`/shutdown against an already-reaped record sends no further signal, so it can never itself land on a reused id. The remaining exposure - the gap between the group emptying and this server's own callback actually running - is disclosed honestly as normally very short but with no fixed upper bound, rather than a wall-clock tolerance it can't back up. `kill_confirmed` reports a STATE (the process group was observed to hold no members), never an ACTION (that a kill was performed) - it can be `true` on a job that simply exited on its own and was never signaled at all.
- Before escalating a `kill()`'s grace-period SIGTERM to SIGKILL, ghantika now checks whether the process group is still the one it spawned: it snapshots the leader plus every currently-live descendant's pid and real, `ps`-read start time right before the SIGTERM is sent, then, once the group survives the grace period, boundedly re-reads only those same recorded members. If any one of them still reports an exactly matching start time the escalation proceeds against the whole group as before; if none matches, escalation is refused and no SIGKILL is sent, disclosed via a new `escalation_refused_reason` field. This is a bounded, conservative check, not a proof: the number of real observations it makes never scales with group size (one batched `ps` read covers however many pids the group has, rather than one call per pid), though that one read still constructs, emits, and parses data proportional to the group's own size, and force-reaps an unresponsive `ps`/`pgrep` rather than leaving it running. This materially narrows, but does not close, the residual already disclosed above between "still alive" and "about to send SIGKILL" - the identity check and the SIGKILL itself remain two separate syscalls. A failed or degraded observation (a timeout, malformed output, or zero usable records) always refuses escalation rather than defaulting to it; the SIGTERM already sent is never held back by an observation failure, and is honestly disclosed as an unconfirmed best-effort send when neither this check nor the earlier pre-signal identity check could confirm anything.
- The actionlint CI job used to fetch and run a script straight off upstream's moving main branch, so what CI actually executed could change with no change to this repository at all. It now downloads the exact v1.7.12 release archive, checks its SHA-256 against a value recorded in this repo before anything is extracted, and only unpacks the verified archive onto PATH for a separate, later invocation - a mismatch stops the job before the archive is ever unpacked.
- The test-harness retry helper added to absorb the birth-identity capture's transient fork-visibility race (`retryBirthIdentityCapture`) checked its deadline only after each attempt had already settled on its own, so a single slow or never-settling attempt was never actually bounded by the configured budget - a hang, not a bounded failure. Fixed by racing each attempt against a timer sized to the real remaining budget rather than checking elapsed time after the fact; a losing attempt's eventual settlement is discarded safely (a no-op rejection handler attached before the race starts) instead of ever surfacing as a process-level unhandled rejection. This also corrects an overclaim this same PR made earlier: `run()`'s own production spawn path does not avoid this race by construction. Firing the capture unawaited protects response latency, but the very first observation it makes is exactly as exposed to the same transient race as every other call site in this codebase - that was true when the earlier claim was written, and the claim was wrong, not the code. The production-side fix for that exposure is tracked as a separate piece of work, deliberately kept off this PR's already-in-review response path.
- A test in `test/kill.test.ts` pinned an exception for one legacy commit's unqualified proof-claim sentence to that commit's own branch sha. A squash merge replaces every one of a PR's internal commits with a single new commit on `main`, so the pinned sha stopped being an ancestor of `main` the moment that PR landed - severing the exception. Fixed by removing the dead entry - its sentence is absent from `main`'s history - and keeping the exception apparatus with an empty list; the two tests that previously assumed a live entry now state the empty case explicitly rather than passing vacuously. A comment at the exception list itself now names the squash trap: an entry keyed to a pre-squash branch commit sha cannot survive this repository's squash strategy.
- Extended the `io.modelcontextprotocol/tasks` adapter so a backgrounded task stays observable for its whole life, not only at start and end. A still-running task now reports a stable `working` status across repeated reads rather than only a start/end snapshot; a completed task's record is removed on the next task read once it ages past a fixed TTL while a still-running task of any age is left untouched; and each new stdout batch wakes a capable client with exactly that batch's new lines, coalesced into one notification per short time window instead of firing once per line or only once at the end. A stream producing output faster than a bounded rate has its own wake notifications throttled and then stopped automatically - the underlying job keeps running and stays reachable by ordinary polling regardless, since the wake is deliberately only an accelerator on top of the existing poll surface, never a replacement for it: `tasks/get`, `output`, and `tail` behave identically whether or not a client listens for the wake at all. No notification fires for the terminal transition itself; a client learns of it through the ordinary poll surface, same as any other status change. Underneath, `jobStore` gained two small generic hooks - one for a job's output as it is produced, one for the moment its state goes terminal - so an interested listener can subscribe to either without `jobStore` knowing anything about Tasks itself; each task's wake logic rides on its own per-task closures over those two subscriptions, while `jobStore` itself holds the persistent listener registrations and the watch-stop annotation for the life of the job record.
- `tasks/cancel` now actually cancels a job instead of just reporting its current state: it signals and reaps the job's whole original POSIX process group by reusing the exact same containment `kill` already provides (grace-period SIGTERM, SIGKILL escalation, the identity checks, the external reap confirmation), so a real, multi-level process tree is genuinely gone afterward, not just the direct child. The request itself is acknowledged as one step, and a later `tasks/get` read separately confirms the terminal `cancelled` status. Same disclosed boundary as `kill`: a descendant that detaches into its own session or process group is neither signalled nor observed by this call.

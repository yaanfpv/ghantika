# Changelog

All notable changes to this project are documented in this file.

## [Unreleased]

- README.md documented the client-side settings Claude Code's auto-background wake needs: a positive `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS` below the client's own MCP tool timeout, alone in an interactive session, plus `CLAUDE_AUTO_BACKGROUND_TASKS` in a non-interactive one. The headline promise was softened to match, since the wake depends on client and configuration rather than being unconditional.
- Updated js-yaml to 5.2.3, typescript-eslint to 8.66.0, and the CodeQL action to 4.37.6.
- Corrected the vendored Tasks-extension schema's own description, which claimed a digest check verifies the adapter conforms to the pin. The check compares the schema file's own bytes to a recorded SHA-256 and nothing else - it never reads the adapter. A narrower version of the same overclaim in the adapter's own header, which said every result shape is checked against the schema, is also corrected: two of three result shapes are checked against the adapter's own emitted output, the third only against a hand-written literal.
- Added `config/tasks-schema-provenance.json`, binding the vendored Tasks-extension schema to the exact upstream commit and bytes it was measured against, with every deliberate divergence from that upstream source enumerated and reasoned - including several not previously written down anywhere: whole categories of upstream shapes this schema never vendors at all, a field it omits that upstream carries, several fields typed stricter than the upstream contract requires, and two fields sourced from a different spec entirely.
- Added `src/wake/resolveWakeTarget.ts`, a pure function that resolves a `WakeTarget` from the raw `_meta` object of an incoming `tools/call` request: `"resolved"` when `meta.threadId` is present and a non-empty string, `"absent"` when `meta` itself is undefined or carries no `threadId` at all, `"malformed"` (with a reason naming what was actually found) when `threadId` is present but is null, a number, an object, an array, or an empty string. `threadId` is treated as a thread-identity signal by this codebase's own design; the function makes no claim about which real client populates it or how. Any handler-visible metadata object lacking `threadId` resolves to the `"absent"` case rather than an error - a fact about this resolver, not a claim about any particular client's shape. Never validates `threadId`'s shape beyond "present and a non-empty string" and never falls back to anything else (an env var, a config guess, a correlation heuristic) when a target cannot be extracted - a caller holding anything other than `"resolved"` has definitively not been given a target. `scripts/check-module-boundaries.mjs`'s `FROZEN_MODULES` now also admits this file.
- Added the transport-layer wake: a mechanism distinct from the MCP notifications sent down an open connection, for eventually resuming an idle agent session on the host machine. `src/server.ts` resolves each `run` call's `WakeTarget` from that request's own `ctx.mcpReq._meta` and passes it to `src/tasksAdapter.ts`, which subscribes a dedicated, independent listener to the job's terminal transition - registered regardless of whether the calling connection negotiated the Tasks-extension capability, since the mechanism never sends an MCP notification down that connection and the underlying job exists either way. The listener unsubscribes itself the instant it fires, so it never outlives the job's own terminal transition. It calls the transport selector only when an internal server-process environment variable is set to the exact string `"1"` (never something an MCP client can set over the wire) and the request's own metadata resolved a target; a malformed target is logged and never acted on, and the call itself is fire-and-forget, never affecting the `tools/call` response it rides alongside. The variable is unset by default, so the mechanism ships inert - the subscription and its listener lifecycle are real, but no transport call happens unless that variable is explicitly set. `src/wake/resolveWakeTarget.ts` is a third admitted public door into `src/wake/` (module-boundary and wake-transport-boundary guards updated to match) since `server.ts` now calls it directly.
- Fixed a real race in `kill_confirmed`'s own write path: `setKillConfirmation` carried a guard that silently discarded a real, external confirmation whenever the eager reap at process exit resolved before the record's own terminal-state transition - Node's `exit` event can fire before either stream's `end` event, so this raced routinely, and once the write was lost, the reap-once tracking had already consumed its one attempt, leaving `kill_confirmed` stuck at `undefined` permanently rather than merely late. The field's own contract never depended on the record's state in the first place - `confirmed` reflects the caller's own knowledge at the moment of the call, whether that is a genuine external check or, for a job that never spawned, a vacuous truth by construction - so the guard was only gating on whether this store's own bookkeeping had caught up, never protecting against a false confirmation; removing it closes the race outright, since no call site can now record a false positive for a group that is genuinely still alive. As defense in depth for the same class of guard elsewhere, the three call sites that gate the reap-attempt flag on the confirmed outcome now gate on the outcome AND the write having actually landed. Those two conditions serve two different purposes: the outcome half is what already lets an unconfirmed, still-live job be retried on a later call; the write-landed half is stale-bookkeeping cleanup for the narrower case where the record itself vanishes out from under a confirmed write (the only production path today is a lazy TTL purge racing an in-flight reap) - `markReapAttempted` has no existence check of its own, so without this half it would still add a reap-attempted entry for a job id `get` can no longer find. A job that never spawned - an invalid cwd, unresolvable executable, or policy denial (settled synchronously as part of the job's own creation), or a genuine async spawn failure past those checks (settled as part of its terminal transition) - now settles `kill_confirmed` to `true` rather than leaving it unset forever, since its process group trivially holds zero members.
- Fixed two further never-spawned paths that omitted the same `kill_confirmed` settling call: a job cancelled while still waiting in the concurrency queue, and a job still queued when the server shuts down. Both settle straight to `killed` without ever spawning a process group, matching every other never-spawned case, but a status-only client polling either kind of cancelled job previously saw `kill_confirmed` simply absent instead of `true`. Regression coverage for the queue-cancellation path now asserts the public projection through real `kill()` and `status()` handler calls, plus a `list()` call checked against its own five-field summary - `list()` was never meant to carry `kill_confirmed` for any job, so that call only confirms the job left the queue, not the field's value. The shutdown-drain path is asserted through a direct `status()` handler call taken after the client transport has already closed, since there is no `kill()`, no `list()`, and no post-shutdown RPC to call there.
- Fixed a real, measured test race in `test/tasks.test.ts`'s run-only-mint-rule test: a naturally-exited job's `state` could read as terminal before its `counts.stdout_lines` had actually caught up, because the test polled only until `state` turned terminal and asserted line counts as if that same poll had covered them too - observed on CI as a job that had already written one byte still reading a `stdout_lines` count of 0. Added a poll that waits for a job's `counts` to hold steady across several consecutive reads before treating them as final (sound because the underlying counters only ever increase), applied it and the existing `kill_confirmed` poll wherever that test reads either field, and found the identical `kill_confirmed` exposure in `test/run.test.ts`'s own direct-handler tests, which spawn through the same code path. Every genuinely safe read is left alone with an inline note explaining why. No production behavior changed - the materialization these tests exercise is correct as built; these were gaps in how the results were read.
- The README now states, per connection era, which Tasks-extension methods currently dispatch. On a legacy (pre-2026-07-28) connection, `tasks/get`, `tasks/update`, and `tasks/cancel` all reach their handlers. On a 2026-07-28-revision connection, only `tasks/update` currently dispatches - the revision's method registry has no entry yet for `tasks/get` or `tasks/cancel`, so a request naming either returns `-32601 Method not found` regardless of capability. The seven tools (`run`, `status`, `output`, `tail`, `kill`, `list`, `follow`) and the poll floor they sit on are unaffected either way; so is the Tasks-capable output/status notification path.
- The README's description of the Tasks-capable terminal status notification now states, in terms, where the mechanism falls short of the released spec. The notification's payload matches the legacy `tasks/get` projection field for field. But on a 2026-07-28 connection, `tasks/get` itself currently returns `-32601 Method not found`, so there is no live method there for the notification to be compared against. And on every connection, this server sends the notification unconditionally to every Tasks-capable connection for every minted task, rather than following the released subscription protocol's task-id opt-in and per-client acknowledged subset.
- Added `follow`, a 7th tool: a bounded wait on a job's next event, returning as soon as new output arrives on the selected stream(s), the job reaches a terminal state, or an explicit `timeout_ms` elapses (defaulting to 45000ms, clamped to a 3600000ms/one-hour ceiling), whichever happens first - a timeout is a normal, non-error result, never a hang, and `status`/`output`/`tail` remain the way to check a job regardless of whether `follow` is ever called. Output arrival means a newly materialized line on the selected stream; a buffered fragment without a terminator does not wake the call on its own, but becomes a partial event when the selected stream finalizes; terminal state can still settle the call. Subscribes to `jobStore`'s own `onOutputArrival`/`onJobTerminal` seams synchronously, before ever checking whether either condition is already true, so nothing can arrive in the gap between "read current state" and "start listening": no other callback can run between those two synchronous steps on a single-threaded event loop, even though the steps themselves still take real time to execute. `stream` scopes the underlying subscription itself, not just the response, so an arrival on an unselected stream never ends the call early. Cancelling the underlying MCP call - closing the connection, or a client sending the standard cancellation notification - now tears down its subscriptions and pending timer immediately rather than leaving them to run to their own natural bound. The server also caps how many `follow` calls may be outstanding at once, across every connection it serves, at 128; a call made once that cap is reached is rejected outright with a tool error, never queued or coalesced with an existing wait on the same job - the cap is enforced process-wide rather than per connection, disclosed as such, since this server tracks no per-connection identity today.
- Fixed a real, reachable gap in `follow`'s cancellation handling: the installed SDK's own `notifications/cancelled` dispatch treats a request id of `0` or `""` (empty string) as absent (its guard is a plain truthiness check, and both are falsy in JavaScript), even though JSON-RPC 2.0 allows either as a legal request id with no reservation on them - so a client whose `tools/call` happened to carry one of those two ids could never have that call's cancellation reach `follow` through the SDK's own path, no matter how correctly the server forwarded its signal, and the call's output/terminal subscriptions and admission-budget slot stayed held until the underlying job reached a terminal state, the call's own timeout elapsed, or the connection closed. Reproduced directly against the installed SDK's own source, and pinned down with a raw-wire test that sends a real `notifications/cancelled` naming `requestId: 0` and, separately, `requestId: ""` over an actual transport, paired with an identical nonzero-id case as a control. Fixed with a second, independent observer chained onto the same wire traffic the SDK's own dispatch already reads, checking a cancellation's `requestId` by type rather than by truthiness, so a falsy id's cancellation is now caught regardless of what the SDK's own guard does with it; every other request id keeps behaving exactly as before, since the two signals are combined with `AbortSignal.any`.
- Fixed a second, narrower gap in the same mechanism: the installed SDK defers actually invoking this server's `tools/call` handler to a microtask, after already registering its own internal cancellation state synchronously, while the new independent observer above runs synchronously on message receipt - so a client sending its `tools/call` request and that same request's `notifications/cancelled` back to back, with no yield between the two sends, could have the cancellation fully processed and discarded before this server's own tracking for that request even existed, letting the call subscribe and hold an admission-budget slot with nothing left to ever cancel it. Reproduced with a raw-wire test that sends both messages with no `await` between them, for both `0` and `""`, and confirmed the call's listeners and admission slot never settle. Fixed by having the observer record an early cancellation it cannot yet apply, consumed the instant the handler registers its own tracking - closing the race regardless of which side happens to run first, bounded by a fixed cap against a client naming request ids that never arrive at all.
- Corrected two claims this changelog and the source comments around the fix above got wrong when the fix landed. First: the independent observer's own check actually runs BEFORE the installed SDK's cancellation dispatch on every message, not after it for every id but `0` as previously stated - `AbortSignal.any` combines both signals regardless of which fires first, so the practical outcome for a nonzero id is unaffected, but the ordering claim itself was backwards. Second: a cancelled `follow` call on request id `0` or `""` does NOT go unanswered the way a cancelled call on any other id does - the installed SDK's own response suppression is gated by the same broken falsy-id guard this fix works around independently, so it never triggers for those two ids, and a normal response carrying `follow`'s own cancellation text is still sent. That asymmetry is disclosed rather than closed, since closing it would mean writing into the SDK's own private internal state from outside it. Also split `follow`'s single cancellation-result message into two distinct ones: a call cancelled before it ever subscribed genuinely never held a subscription or an admission-budget slot, while a call cancelled mid-wait held both and had them released - the one shared message previously used at both sites carried the first call's own truth into the second, where it no longer held.
- `scripts/check-wake-transport-boundaries.mjs`'s `isPermittedWakeTestFile` now also admits a `test/fixtures/wake-*.ts` fixture spawned as a real, separate OS process by a `test/wake-*.test.ts` file, alongside the `test/wake-*.test.ts` file itself - a narrow, explicit addition (`wake-` prefix, directly under `test/fixtures/`, never every file that directory contains) covering the live case this guard's own header already disclosed as a scope boundary: `test/fixtures/wake-app-server-crash-harness.ts` reaches `appServerTransport.ts` via `../../dist/wake/appServerTransport.js` to run it outside the test process. That header comment, and every other stale reference elsewhere in this file's comments and violation message to the narrower `test/wake-*.test.ts`-only exemption, are updated from hypothetical ("a test file that reaches...") to name this fixture as the real, already-happening instance. Proven both at the predicate level and end to end through `checkWakeTransportBoundaries` on a scratch tree: a `test/fixtures/wake-*.ts` fixture reaching a non-public wake file directly produces no violation, while an otherwise-identical sibling fixture that does not carry the `wake-` prefix still does.

Proven with a negative control: a deliberately planted failure now fails in 137ms with the assertion named, restored to green afterward. The golden was deliberately regenerated (never silently re-baselined) from a real spawned build at the exact commit that has `follow` merged but predates the wake-transport-layer's own wiring into the tasks adapter and server dispatch, via a new, explicitly manual `scripts/capture-plain-poll-golden.mjs` that is never invoked by any test run, guard, or CI job. The new `follow` scenario exercises a genuine bounded, non-instant wait (a real ~200ms delayed write, resolved via subscription rather than an already-satisfied immediate return) so it actually says something about the one tool that can differ from an instant response. The canonicalization/extraction logic both the capture script and the live comparison test rely on now lives in one shared `test/helpers/plainPollCanonicalization.ts` module, imported by both, rather than being defined twice.
- Sharpened `selectAndWake`'s exhaustion `detail` for the one client none of today's `DEFAULT_TRANSPORTS` serve at all: when every transport reports `"unavailable"` and this process is itself running under Claude Code (`CLAUDECODE === "1"`, the one signal Claude Code documents as set for a stdio MCP server subprocess it spawns), the aggregate message now leads with a plain sentence naming the client mismatch and the poll floor (`status`/`output`/`tail`) as the real working path, instead of reading as two unrelated per-transport near-misses - the full per-transport log still follows underneath, unchanged, for anyone who wants the mechanical detail. Applies to the `"unavailable"` outcome only, never `"refused"` (a refusal means something live actually answered, and that answer is left exactly as-is), and only when at least one transport was genuinely configured to try. Every other caller - not running under Claude Code, or on the `"refused"`/empty-list paths - sees exactly the prior generic wording; `selectAndWake`'s own signature, its strict `"delivered"` short-circuit, its throw-handling, and how `"refused"` vs `"unavailable"` is decided are all untouched. No transport was added and nothing changed about which transports are tried or in what order - this is message text only, on the one path that already had nothing better to say.
- Added `fswatch` to the test suite's shared command-policy allowlist fixture (`test/fixtures/policy-allow.json`). Without it, `test/dogfood.test.ts`'s real `run()` call denied the command outright and settled its job to `failed` rather than `working` on any host where `fswatch` happens to be installed and the test therefore actually executes instead of skipping - confirmed directly on a real host meeting that condition, where the test failed for exactly this reason before this fix, and passed once the allowlist carried the one binary that test's own proof depends on. Also added a broad-net absence-oracle assertion to that same test's post-kill rollback check: once cleanup completes, it now confirms no process whose own command line references the scratch mailbox path - not merely nothing `fswatch`-shaped - still does, matching the narrow-plus-broad pairing every earlier checkpoint in that file already uses around the job's live lifecycle.
- Added `src/wake/selectTransport.ts`, the ordered wake-selection function (`selectAndWake`) a real caller actually invokes to request a wake: it tries each configured `WakeTransport` strictly in array order - never concurrently - probing before waking, calling `wake()` only when `probe()` reports available, and stopping the instant a transport's own `wake()` resolves with `outcome: "delivered"`. That is the only path through the whole function capable of returning `"delivered"`; a refused or unavailable attempt is recorded and the loop moves to the next transport, and a transport whose `wake()` throws or rejects is treated the same way rather than crashing the caller. When every transport is exhausted, the aggregate result is `"refused"` only if at least one transport was genuinely attempted and actively declined, `"unavailable"` otherwise (including an empty transport list) - a documented choice, since "something live said no" and "nothing here could be reached" call for different caller behavior - and its `detail` enumerates every transport tried, in order, and exactly why each one fell short, never a bare "nothing worked." Also exports `DEFAULT_TRANSPORTS`, the real app-server-then-desktop-IPC ordering a real caller passes in, chosen because the app-server transport has one well-defined unavailability reason against a documented subcommand while the desktop-IPC transport depends on a live GUI window and an undocumented, already-once-relocated socket. Because the selector needs to import both concrete transports directly - something `wakeTransport.ts`'s single-file boundary couldn't accommodate without breaking that file's own zero-runtime-export guarantee - `scripts/check-wake-transport-boundaries.mjs`'s boundary now admits a small, explicit set of two public files (`WAKE_PUBLIC_FILES`) rather than one; `appServerTransport.ts` and `desktopIpcTransport.ts` stay exactly as non-public as before, still refused when imported from outside `src/wake/`. Wired into `tasksAdapter.ts` below, in this same release.
- Fixed a real, observed-on-CI test race where `kill_confirmed` was read from a `kill()` response captured before its own async confirmation write had actually landed - the field is set by a confirmation callback inside `kill`'s own implementation, and the gap between the process group actually emptying and that write landing is real event-loop scheduling latency with no fixed wall-clock bound, so the read could win the race on a loaded runner. Fixed in `test/tasks.test.ts`'s run-only-mint-rule test and in `test/kill.test.ts`'s process-group-reap test by polling (via repeated, idempotent `kill`/`status` calls against the same job) until the field has actually settled, matching this suite's own established pattern for the same gap under its other trigger (a job's leader exiting naturally). A follow-up sweep of every other site in `test/kill.test.ts` reading this field from a previously-captured response found one more genuine instance with the identical shape - a poll loop that waited for a job's own terminal state but not for `kill_confirmed` alongside it - and fixed that too; every other site was reviewed and left as-is with a comment recording why it is safe (either the poll loop guarding it already covers the field, or the code path itself resolves the confirmation synchronously before the response is ever generated).
- Added `src/wake/appServerTransport.ts`, a concrete `WakeTransport` that wakes an idle Codex thread by spawning the `codex app-server` subcommand and driving its newline-delimited JSON-RPC protocol over that subprocess's own stdio (one JSON object per line, no `Content-Length` framing - confirmed by spawning a real, stock `codex app-server`, CLI 0.147.0, and reading its raw stdout bytes). Sending `thread/goal/set` with `status: "active"` for an idle thread starts a model turn there, with the caller's objective text reaching the model verbatim; `probe()` verifies at runtime, on every call, that the running app-server's `experimentalFeature/list` actually reports the `"goals"` feature enabled, never assuming it stays true across a restart of the process it probes. Every goal this transport arms carries a `tokenBudget` - a real field on the protocol's own request shape, enforced server-side - and every spawned child is additionally bounded client-side by a wall-clock ceiling on how long it may keep running once a wake has delivered, independent of what the server side enforces; both bounds are disclosed as deliberately modest, round defaults rather than measured ceilings, since a previously-reported high-turn-count figure did not reproduce under independent, controlled measurement. `wake()` resolves as soon as delivery is confirmed (a `turn/started` notification observed for the target thread) rather than blocking for the whole triggered turn - the spawned process is the very thing executing that turn, so killing it the instant delivery is confirmed would abort the work just started. The child is instead handed to bounded background supervision that keeps it alive until either the turn concludes or the wall-clock ceiling is reached, then reaps it (`SIGTERM`, a grace period, `SIGKILL` if still alive, and a real wait for the OS to confirm it is gone), tracked per transport instance with a `process` exit listener installed only while that instance has a live child to protect - so a hard crash elsewhere in the process still gets a best-effort `SIGKILL` pass without leaking one listener per constructed instance. Reaches only the documented public subcommand (plain `codex app-server`, stdio transport, never `daemon start`, no private socket path, no modified binary).
- Added `src/wake/desktopIpcTransport.ts`, a `WakeTransport` that wakes a Codex conversation running inside a live ChatGPT desktop app window by talking directly to that app's own local IPC bus over a Unix domain socket - confirmed today against a real session as a 4-byte little-endian length-prefixed JSON exchange over `~/.codex/ipc/ipc.sock`: `initialize` to obtain a `clientId`, `thread-owner-discovery` to find which connected client currently has the target conversation open, then `thread-follower-start-turn` targeted at that owning client. Everything this transport touches is a closed, undocumented internal of the app's own bundled code rather than a published API, and it is fenced accordingly: `probe()` checks, in order, that the socket path exists, is actually a socket, is owned by this process's own uid, and genuinely answers a real `initialize` call, failing soft with a specific diagnostic on any deviation rather than crashing or guessing; the socket path itself already relocated once, inside a single app update earlier today, from an older per-uid temp path, and that same update silently dropped an unrelated local feature entirely, both disclosed directly in this file's own header. The owner gate `thread-owner-discovery` enforces - only a client with the conversation genuinely open in a live window may start a turn on it - is honored rather than routed around: a missing owner (measured today as a `no-client-found` result for every thread not currently open in a window) reports `refused`, never forged or retried into looking like a hang, and `thread-follower-start-turn` is never attempted without a real owner id the discovery call itself returned. This transport reads no credential, makes no network call, and requires no pairing; its whole authorization model is being the same OS user as the socket's owner. It implements no preference ordering against the separate, durable `codex app-server`-based transport a sibling story is building - that selection logic remains out of scope for both. Tested against a fake local Unix domain socket server built independently of this transport's own framing code, covering the wire round-trip (chunked/multi-frame/partial delivery, an oversized declared length, malformed JSON), the owner-gate and its race with a closing window, and every fencing branch `probe()` checks.
- Added `src/wake/wakeTransport.ts`, the single `WakeTransport` contract every future wake mechanism will implement (`probe(): Promise<Capability>`, `wake(target, payload): Promise<WakeResult>`), plus a boundary guard (`scripts/check-wake-transport-boundaries.mjs`) that keeps every transport-specific symbol confined to its own file and its own tests, enforced in CI alongside the five existing source guards. `probe()` must report a real, freshly-observed result (never a platform guess) with a stated reason on failure, and is never cached by the interface itself - the caller states and justifies its own cache lifetime, if any. A wake result distinguishes delivered, refused, and unavailable as three separate outcomes rather than collapsing to a boolean, since "this will never work here" and "this failed just now" call for opposite remedies. This module is purely type-level - it compiles to an empty runtime file - so it adds zero transports and zero runtime cost on its own; ghantika continues to start and serve its existing tools exactly as before with none registered, which is the supported baseline this and every future transport are built against. This is not `src/tasksAdapter.ts`'s own output-driven wake-on-output mechanism (`notifications/ghantika/outputWake`) or the released Tasks extension's own `notifications/tasks` status notification, both unrelated pre-existing features that happen to share the same English word.
- `kill_confirmed` is written by an async confirmation callback whose gap versus the calling response is real event-loop scheduling latency with no stated upper bound, documented as such in `src/tools/kill.ts` - so a fixed wall-clock deadline on that field settling is a bound on a quantity the contract says has none, and one lost on a loaded CI runner. Nine call sites across `test/tasks.test.ts`, `test/kill.test.ts`, and `test/run.test.ts` now poll `kill_confirmed` without a time limit instead, all removing a `Date.now()`-based deadline that previously threw once exceeded: `test/tasks.test.ts`'s shared `pollUntilKillConfirmed` helper, used at 2 call sites; 4 further sites in `test/kill.test.ts` with the identical inline shape; and `test/run.test.ts`'s own shared `pollUntilKillConfirmed` helper, used at 3 call sites, carrying the identical deadline-plus-throw shape as the other two files' sites. Every site relies on the surrounding test's own runner timeout as the backstop for a genuine hang, and logs a one-line breadcrumb to stderr on a fixed cadence while still waiting, carrying the same job snapshot the old failure message did. A new check, `scripts/check-no-bounded-kill-confirmed-wait.mjs`, detects the specific pattern that caused this: a loop referencing `kill_confirmed` that also contains an `if (Date.now() > ...)` guard followed by a `throw`. It does not detect an equivalent deadline built from a different clock source (an aliased or global `Date.now`, `performance.now()`) or a control-flow shape other than `if`-plus-`throw`.

- `tasks/get`, `tasks/update`, and `tasks/cancel` now implement the Tasks extension's released 2026-07-28 contract directly, replacing the pre-finalization shapes they carried before: `tasks/get` throws a real `-32602` for an unknown or expired taskId instead of returning a tagged not-found result; `tasks/update`'s complete behavior is an existence/TTL check followed by a fixed acknowledgement, since no ghantika task ever reaches `input_required`; `tasks/cancel` keeps its real process-group kill/reap effect but now returns that same fixed ack, matching the spec's own eventually-consistent contract instead of reading a fresh snapshot back. `TASKS_CAPABILITY_DESCRIPTOR` drops its invented `methods` key - the spec's own capability schema forbids any key at all. The status set this adapter emits is now checked as a subset of the spec's five-value enum rather than an equal set, since `input_required` is structurally unreachable for a job-backed task. Jobs gain a `last_updated_at` field, advancing on every materialized output line and every terminal transition, backing the contract's `lastUpdatedAt`. A task's own notification-watch auto-stop now surfaces correctly both mid-run (`statusMessage`) and at a terminal state (nested under `result`/`error`).

- Added support for the MCP 2026-07-28 revision's `server/discover` opening exchange over stdio, served alongside the existing legacy `initialize` handshake via the installed SDK's `serveStdio` entry point (`@modelcontextprotocol/server/stdio`), which owns the era decision per connection and pins one `Server` instance from a shared factory for that connection's lifetime - including discarding an optimistic `server/discover` probe and building a fresh instance from the same factory if the client falls back to `initialize`. The three transport-level guarantees this server depends on all had to move, not just get exercised again: the initialize-gate (a security control that blocks `tools/call` until a real, successful handshake has completed) now wires its two observers by overriding `.connect()` on the constructed `Server` instance itself, since a pinned instance under `serveStdio` connects to an internal `StdioConnectionChannel` proxy this file never otherwise sees a reference to, rather than the real wire transport the previous code attached its observers to directly. A modern-era connection has no `initialize`/`notifications/initialized` exchange for the gate to observe at all, so its own trust anchor is `serveStdio`'s own pre-connect `setNegotiatedProtocolVersion` call - confirmed, not assumed, that nothing can reach the connected instance before that call has already run. - Added a concurrency cap and a bounded FIFO queue in front of `run()`'s spawn, so a burst of jobs runs under an honest, configurable bound instead of exhausting the host. A job arriving while the cap is full and the queue has room reports the existing `starting` state with a new `queue_position` field rather than a sixth job state; one arriving once both are full is rejected immediately, with a typed diagnostic and no job ever created - `run()` returns instantly in every case, never blocking on a slot. A concurrency slot is held for as long as a job is running or still being cleaned up after exit, released only once its process-group reap has actually confirmed the group empty. A reap that runs but cannot confirm leaves the slot held, tracked as stranded and retried automatically a bounded number of times, or separately recoverable by a manual `kill()` call against the same job. Neither retry path ever sends the group a further signal, though: by the time a retry runs, this server can no longer confirm the tracked process-group id still names the group it originally spawned rather than an unrelated one that has since reused it, so a retry only ever re-checks existence. A group still genuinely alive at that point stays a disclosed, unconfirmed residual instead of receiving a second signal; one that has since genuinely emptied is correctly recognized and recovered, still without ever being signaled again. The task-record TTL purge never reclaims a job while its slot is still stranded, so the only durable trace of a held slot is never silently erased before it can be recovered - a job becomes purgeable again the moment its slot is actually confirmed. A job that fails to spawn once it reaches the front of the queue settles to `failed` and its slot is freed rather than left stuck. A job that never reserved a slot at all - one whose invalid cwd, missing executable, or policy denial settled it to `failed` before admission control ever ran - could still have its terminal `kill()` call decrement the shared active-slot counter, silently freeing a different, genuinely-running job's reservation and letting real concurrency exceed the configured cap; a slot is now released only for a job id this store itself recorded as having actually reserved one.
- Added retention for a finished job's buffered output: it becomes eligible for reclamation once `GHANTIKA_JOB_RETENTION_MS` milliseconds have elapsed since the job ended (default one hour) or the number of eligible finished jobs still holding output exceeds `GHANTIKA_MAX_RETAINED_JOBS` (default 200), whichever comes first - oldest-ended evicted first once over the cap. A job that genuinely never received any output on either stream is never itself a candidate, so it can't displace an older one that still holds real output; a job whose only content is a not-yet-newline-terminated fragment IS still a candidate, since that fragment is real received bytes. Reclamation happens either immediately, opportunistically, the next time any job is created - often the earlier path - or, on an otherwise-idle server, via a check scheduled every 30 seconds through an ordinary `setInterval`. That schedule is not a wall-clock guarantee: the callback only runs once the event loop is free to reach it, so a check can be delayed past its scheduled moment by other synchronous work or host load, the same way any `setInterval` callback can be. Ordinary reclamation for an eligible job on an otherwise-idle server lands close to the configured retention window plus one scheduled interval, and that margin can widen under load rather than holding as a hard ceiling. A still-running job's output is never reclaimed. A job's output is also held past its retention window for as long as its own process-group reap decision is still being awaited - the window from a reap decision starting to be awaited to that decision settling, specifically; a job marked terminal by a different path (the optional per-job deadline timeout, or a live `kill()` call) before that window starts is not covered, a pre-existing gap retention makes reachable rather than creates, and closing it is tracked separately. - A job's client-visible terminal state (`exited`/`killed`) now orders after its own last output event, when this job's own leader-exit reap CONFIRMS its process group empty AND no descendant has left that group: it no longer fires the instant the leader process exits, before a stream's already-buffered output has finished draining or before a backgrounded grandchild that inherits the job's stdio has closed it. This is proven, not assumed - a process's file descriptors close synchronously as part of its own exit, so once every member of the job's own process group is confirmed gone, every write end that group ever held is already closed and the stream's own `end` follows promptly, verified directly against real spawned-process timing. Two disclosed residual cells, one consequence: the reap can instead settle unconfirmed (zero survivors was never externally established) or errored (a real signal-send failure), leaving a same-group process potentially still alive and holding a stream; or a descendant that has detached into its own process group can still hold a stream open indefinitely after leaving the job's group, since process-group membership and file-descriptor possession are independent facts a group-scoped reap cannot see past by design. Both the property and the residuals are POSIX-only - a Windows job's child is never made its own process-group leader, so there is no group for this reap to confirm on that platform.
- `status` now also reports the OS process it tracked for a job, once it ever had a real one: a `pid` field alongside `birth_identity`, never the pid alone, since a pid is reusable the moment its process exits and a bare match would silently inherit that race. `birth_identity.state` is `pending` (the async capture kicked off at spawn hasn't settled yet), `captured` (a real identity is present under `identity`), or `unavailable` (the capture failed, or was never attempted - a job that never got a real process carries neither field at all). A terminal job keeps both the pid it had and whatever capture state actually holds by then - pending, captured, or unavailable - so a stale-looking pid can be verified rather than trusted blind. `identity` is platform-tagged the same way `kill`'s own pre-signal check already is: an exact kernel start-time counter on Linux, a real but probabilistic `ps`-observed elapsed-time correlation everywhere else on POSIX, and `unavailable` on Windows, where this capture isn't attempted - never silently backfilled from this server's own wall-clock spawn timestamp, which this codebase has always treated as too weak a signal for identity.

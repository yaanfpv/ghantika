# Changelog

All notable changes to this project are documented in this file.

## [Unreleased]

- Added public CI on GitHub-hosted runners: build, typecheck, lint, and the full operating-system by Node-version test matrix, plus CodeQL, semgrep, zizmor, and actionlint, all aggregated behind one required `gate` check.
- Added a blocking Prettier format check and a coverage job (an absolute per-metric floor, plus an informational delta against a checked-in baseline) to CI, both required by `gate`.
- Fixed the CI test job never building before running tests, added a `ghantika` executable via `bin`/shebang/`prepack`, and updated dependencies.
- Bumped `typescript-eslint` to 8.65.0 and the `@modelcontextprotocol` SDK packages to 2.0.0-beta.5.
- Fixed the test suite hanging on Windows: added a 30-second per-test timeout and a 15-minute CI job timeout, and gave the handful of tests that exercise real POSIX process-group primitives (`pgrep`, `ps`, negative-pid signaling) a named skip on that platform instead of hanging indefinitely. Windows stays a fully supported platform and a fully supported CI leg; only these specific test-harness primitives lack a Windows-equivalent path today.
- Replaced the `node --test '<glob>'` invocation behind `npm test`/`npm run coverage` with `scripts/run-tests.mjs`, which discovers test files itself instead of handing a glob to a shell (the glob was reaching `cmd.exe` unexpanded on Windows and silently running zero tests) and adds two failure modes a per-test timeout can't catch on its own: an idle watchdog and a wall-clock cap that name the stuck test by file instead of leaving CI to die at the job ceiling with no diagnostic, plus a check for a file whose tests all pass but whose own process never exits.
- Removed a temporary Windows diagnostic workflow whose control could never have passed, by construction. It genuinely planted a real event-loop hold via `setInterval` with no `unref()`, so the held process had no way to exit on its own - the only thing that could ever end it was the inner test process's own hardcoded 30-second timeout. The workflow's outer check ran at a hardcoded 45-second bound and asked whether the process was still alive at that point; its header treated "45 seconds, comfortably past the inner 30-second timeout" as a safety margin, but being past the inner timeout is exactly what guarantees the inner timeout kills the process first, every time, before the outer check can ever find it still running. The relationship between the two bounds made the control's stated pass condition unreachable on any platform, in any run - not a one-off failure, a structural impossibility in how the two timeouts were composed. The real CI gate reproduces the underlying Windows test failures independently of this workflow. (Correcting the removal commit's own message, `225a0665`: it said the control "never actually hung" - it did; the hold was real. It said "the run couldn't have told the difference between a real hang and a clean pass," true of that run but framed as one run's outcome rather than the only outcome the design could ever produce. It also said "nothing it ever produced was usable evidence," which overstates a single design defect into a blanket claim. All three retracted; the precise claim is the one stated above.)
- Fixed six `test/process.test.ts` failures that only showed up on real Windows CI, diagnosed individually rather than as one batch: two tests hardcoded POSIX fixtures (`/bin/sh`, a `PATH`/`HOME`-only exclusion list) that don't exist or don't apply on Windows; one asserted the platform shell's output byte-for-byte instead of tolerating `cmd.exe`'s own line-ending and whitespace conventions; one assumed a `cwd`-is-a-file spawn failure always arrives synchronously, which is a POSIX-only delivery detail (Windows reports it asynchronously, through the same `onError` path a missing binary already uses); and one didn't yet account for the fixed set of environment variables libuv force-injects into every Windows child. A sixth (checking for a missing POSIX execute bit) has no meaningful Windows equivalent for a file addressed by explicit path, so it's now skipped there with a stated reason instead of silently mismeasuring something Windows can't express. Also documented, in place, exactly why an internal `ps`-based process-identity check is safe to remain POSIX-only: both of its real callers already branch around it on Windows before it's ever reached.
